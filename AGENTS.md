# Инструкции Codex для дипломной CRM

## Цель
Разработать оригинальную веб-ориентированную CRM для небольшого предприятия на Python, Django 5.2 LTS, SQLite, Django Templates и Bootstrap. Работа ведётся маленькими проверяемыми итерациями. Срок ограничен: приоритет у работающего и понятного MVP.

## Академическая добросовестность
- Репозитории из раздела «Референсы» служат только для сравнения возможностей и архитектурных подходов. Не копировать исходный код, HTML, стили, README, тесты или формулировки из них.
- При необходимости использования стороннего кода сначала сообщить об этом, проверить лицензию и явно зафиксировать происхождение и обязательную атрибуцию. Не добавлять такой код без согласования.
- Не заявлять об уникальности, проценте антиплагиата или прохождении проверки без фактических оснований.
- Документировать собственные проектные решения, ограничения, реальные результаты тестов и источники. Не выдумывать измерения и результаты.
- Соблюдать правила учебного заведения об использовании ИИ; сохранять понятную историю изменений.

## Ограничения разработки
- Только одна итерация за один запрос. Не начинать следующую без явного разрешения пользователя.
- Не внедрять React, Celery, Redis, Docker, микросервисы и внешние платные API без отдельного решения.
- В первой итерации не реализовывать CRM-модули, модели Client/Request/Deal/Task и пользовательские бизнес-страницы.
- По умолчанию использовать стандартную аутентификацию Django и серверный рендеринг.
- Перед изменениями изучать README.md, docs/TECHNICAL_SPEC.md, docs/DEVELOPMENT_PLAN.md, docs/PROGRESS.md и существующие тесты.
- Не удалять и не переписывать чужие изменения без объяснения. Не выполнять разрушительные команды без согласования.

## Протокол итерации
1. Кратко описать цель, затрагиваемые файлы, критерии приёмки и риски.
2. Реализовать только согласованный объём.
3. Добавить или обновить тесты; проверить позитивные, негативные и граничные сценарии по мере применимости.
4. Запустить доступные проверки и указать точные команды и результаты. Если проверка не выполнялась — так и написать.
5. Кратко обновить docs/PROGRESS.md: статус, сделанное, изменённые файлы, результаты проверок, ограничения и следующий шаг. Подробные результаты держать в одном разделе или протоколе этапа, со ссылкой из журнала. README.md обновлять при изменении актуальных возможностей, запуска, проверочных команд или ограничений; не добавлять туда исторические отчёты.
6. Остановиться и ждать проверки пользователя. Не объявлять этап завершённым, если критерии не соблюдены.

## Качество и безопасность
- Не хранить пароли, секретные ключи и реальные персональные данные в Git. Использовать тестовые данные.
- Использовать ORM Django, CSRF-защиту, валидацию форм и проверки прав доступа.
- Стараться писать небольшой понятный код, понятные имена и краткие комментарии только там, где они помогают.
- Перед завершением итерации запускать `python manage.py check`, `python manage.py test` и, если применимо, `python manage.py makemigrations --check --dry-run`.
- Не утверждать, что проверка пройдена, если команда не запускалась или завершилась ошибкой.

## Файлы и проверочные артефакты
- Перед созданием файла проверить существующие. Выделять отдельный файл при самостоятельной ответственности, пользе для читаемости или тестирования; не объединять разные компоненты ради количества файлов.
- README описывает текущую версию и запуск; история хранится в docs/PROGRESS.md, архитектурные решения — в docs/ARCHITECTURE_DECISIONS.md.
- Результаты этапа отражать в одном компактном существующем разделе или документе. Постоянные доказательства сохранять по правилам ниже; временные технические результаты оставлять вне Git.
- Новый проверочный Python-скрипт добавлять при необходимости повторного использования, предварительно изучив существующие тесты и скрипты.
- Удаление и объединение выполнять после согласования перечня, назначения, зависимостей и способа сохранения важных сведений. До удаления проверять восстановление через Git. Не сокращать миграции и тесты ради количества файлов.

## Постоянное хранение результатов в GitHub
- GitHub — основное постоянное хранилище исходников и значимых результатов разработки. Итоговый код и актуальную документацию каждого этапа сохранять в репозитории в соответствии с согласованным порядком коммита и отправки изменений.
- Все материалы, которые пользователь должен просматривать или проверять после завершения этапа, сохранять в GitHub. Скриншоты, схемы, сравнения и другие постоянные доказательства размещать в `docs/evidence/<номер_этапа>/`; полезные уникальные измерения хранить рядом.
- Связывать результаты визуальных проверок с соответствующей существующей документацией: относительные ссылки на материалы, их назначение, сравнения и результаты измерений. Не создавать отдельные большие отчёты на каждую страницу.
- Не полагаться исключительно на `/workspace/...` и временные артефакты Codex. ZIP в рабочем пространстве не является достаточной передачей материалов пользователю. Необходимые доказательства должны входить в актуальный репозиторий и скачиваться вместе с ним через GitHub Code → Download ZIP.
- Не помещать в Git временные SQLite, логи, резервные копии, секреты, `.env`, Playwright traces и промежуточные файлы. Эти ограничения не запрещают согласованные постоянные изображения и измерения в evidence.
- Перед коммитом проверять изображения и документы на секреты, персональные данные и реальные клиентские данные; для доказательств использовать вымышленные данные.
- Сначала искать уже созданные материалы: сохранять существующие оригиналы, не создавать их повторно. Не дублировать один набор изображений одновременно отдельными файлами и ZIP внутри репозитория.
- В итоговом сообщении каждого этапа указывать ссылку на опубликованный коммит и перечень сохранённых материалов. Проверять целостность изображений и относительные ссылки; временные ссылки не заменяют постоянные GitHub-ссылки.
