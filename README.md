# Дипломная CRM

Веб-приложение для небольшой организации: клиенты, заявки, задачи, сделки и история взаимодействий. Монолит на Python 3.12, Django 5.2 LTS, SQLite и Django Templates; интерфейс на русском языке, собственные локальные CSS и минимальный JavaScript.

Текущая функциональная версия — **8Б**. Полный набор содержит **333 автоматических теста**: 267 CRM и 66 отдельного вычислительного модуля. Финальный этап 9 ещё не начат; история разработки и результаты проверок находятся в [PROGRESS](docs/PROGRESS.md).

## Возможности и роли

| Раздел | Возможности |
|---|---|
| `/` | Имя и роль, текущие доступные заявки/задачи и их просрочки, POST-выход |
| `/clients/` | Общая клиентская база, создание/редактирование, поиск, фильтр организации, сортировка и пагинация |
| `/requests/` | Заявки клиентов, статусы, ответственный, срок, поиск/фильтры; при создании — одна автоматическая задача |
| `/tasks/` | Ручные и автоматические задачи заявок, сроки, статусы, дата завершения и вычисляемая просрочка |
| `/deals/` | Сделки с положительной Decimal-суммой, пятью этапами, ответственным и планируемой датой закрытия |
| `/deals/kanban/` | Пять колонок; смена этапа формой или drag-and-drop, проверка версии карточки и конфликт 409 |
| `/interactions/` | Ручная история звонков, встреч, переписки и комментариев; поиск/фильтры и последние десять доступных записей в клиенте |
| `/analytics/` | Семь показателей, диаграммы этапов/типов, таблицы и текущие просрочки; всё время, последние 30 суток или даты UTC |

- **Администратор** — активный `User` с `is_superuser=True`: все записи, назначения и удаления; управление пользователями через `/admin/`. Доступ к Admin определяется суперпользователем независимо от `is_staff`.
- **Менеджер** — активный обычный пользователь: общие клиенты, свои заявки/сделки/взаимодействия. Задача доступна, когда и она, и её заявка назначены этому менеджеру. Удаление CRM-записей и доступ в Admin запрещены, в том числе при ошибочно включённом `is_staff`.

Вход по логину и паролю — `/login/`; публичной регистрации нет. Неверные данные показывают ошибку, неактивные пользователи не входят. Выход выполняется POST-запросом с CSRF; GET `/logout/` возвращает 405. Внешние адреса `next` отклоняются. Изменяющие формы защищены CSRF; удаление требует подтверждения и POST.

## Локальный запуск

Проверено на Python 3.12.14 и Django 5.2.18. Из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
python manage.py migrate --noinput
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Откройте `/login/` на локальном сервере и войдите созданным администратором. Готовые учётные записи не поставляются. Ключ храните в безопасном локальном окружении, вне Git. В новом терминале активируйте venv и задайте тот же `DJANGO_SECRET_KEY`, чтобы сохранить действительность сессий.

Чтобы создать менеджера, откройте `/admin/` → «Пользователи» → «Добавить пользователя». Задайте логин и пароль; оставьте «Активный» включённым, «Статус персонала» и «Статус суперпользователя» — выключенными.

## Миграции и обновление

Перед обновлением своей базы остановите приложение и сделайте резервную копию SQLite. Затем в активном окружении с заданным ключом:

```bash
python manage.py showmigrations crm
python manage.py migrate --noinput
python manage.py migrate --check
```

В репозитории шесть последовательных CRM-миграций, `0001_initial`–`0006_clientinteraction`. Не удаляйте и не пересоздавайте их ради обновления. После обновления перезапустите сервер.

**Рабочая БД текущей облачной среды ожидает существующую `0006_clientinteraction`: `migrate --check` возвращает 1.** Очистка файлов её не изменяет и миграции на ней не применяет. Проверки полной схемы выполняются отдельно на временной SQLite. Наличие миграции в Git само по себе не означает её применение в рабочей базе.

## Проверки

Из корня, в активированном окружении с `DJANGO_SECRET_KEY`:

```bash
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
python -m pip check
```

Ожидаются 333 теста, включая все 267 прежних CRM-тестов. Django runner создаёт отдельную тестовую БД; тесты миграций изменяют только её. Последние фактические команды, коды завершения и ограничения — в [журнале](docs/PROGRESS.md#m2-experiments).

Чистый исследовательский модуль распределения работает на синтетических данных без Django-сервера, настроек и БД. Быстрый эксперимент и его отдельные тесты:

```bash
python scripts/run_optimization_experiment.py --preset smoke
python -m unittest crm.test_optimization
```

По умолчанию эксперимент выводит результат в терминал. Необязательный `--output /tmp/crm-m2.json` сохраняет JSON вне репозитория. Масштабы, лимиты, точные результаты и ограничения — в [OPTIMIZATION_EXPERIMENTS](docs/OPTIMIZATION_EXPERIMENTS.md); назначения в CRM этот модуль не сохраняет.

Сохранены повторно используемые HTTP/Chromium-сценарии: [Kanban](scripts/verify_stage6c.py), [история взаимодействий](scripts/verify_iteration7.py), [аналитика и диаграммы](scripts/verify_iteration8b.py). Для них отдельно нужны Python с Playwright и установленный Chromium; это инструменты проверки, не зависимости приложения. Например:

```bash
python scripts/verify_iteration8b.py --python /path/to/app-venv/bin/python \
  --chromium /path/to/chromium --artifacts /tmp/crm-analytics
```

Скрипт использует вымышленные данные, собственные временные настройки/SQLite и сервер. Путь `--artifacts` задавайте вне репозитория. Правила и ограничения повторения описаны в соответствующих протоколах ниже.

## Существенные правила и ограничения

- Общая клиентская база не расширяет доступ к чужим заявкам, задачам, сделкам или истории. После переназначения заявки прежние задачи автоматически не переназначаются: администратор исправляет назначение вручную.
- Новая заявка через CRM создаётся в `new`. Автоматизация работает через явный сервис создания, в одной транзакции; повторная отправка формы может создать другую заявку с другой задачей. Удалённая автоматическая задача может быть явно восстановлена сервисом. Обычный ORM сам автоматизацию не запускает.
- Просрочка — запись в new/in_progress со сроком строго раньше текущего времени; она вычисляется при просмотре. Завершение заявки и задачи независимо. Ввод/отображение времени — UTC, точность пользовательского поля — минуты.
- `Task` связан только с заявкой. Связь задачи со сделкой из FR-06 не реализована. Вместо Bootstrap используется локальный CSS; исходное [ТЗ](docs/TECHNICAL_SPEC.md) сохранено без подмены требований.
- Денежный ввод — Decimal, диапазон одной сделки `0.01–9999999999.99`. Прямые ORM/SQL-записи SQLite могут нарушать точность и диапазон; доверенным скриптам нужны Decimal из строк и `full_clean()` перед `save()`. После преобразования ORM исходные лишние знаки иногда уже не видны (`1.234 → 1.23`).
- Аналитика отражает текущие этапы сделок, **созданных** за период. Конверсия — `won/(won+lost)×100`; сумма won не является полученной выручкой. Даты фактического закрытия, оплаты и история этапов не хранятся. Ошибка денег делает весь денежный итог недоступным, не заменяет его нулём. Формулы, округления и границы гарантий — [ANALYTICS_METRICS](docs/ANALYTICS_METRICS.md).
- Защита версии действует на смену этапа Kanban; общего контроля конкурентного редактирования CRUD и единого снимка нескольких SELECT нет. При неопределённом результате сети доску нужно обновить. Нативный drag-and-drop проверен не на всех сенсорных устройствах; формы остаются доступны без JS.
- В изолированном тесте повреждённых сумм зарегистрировано отложенное исключение SQLite-курсора. Оно не объявляется исправленным; [исходный журнал](docs/validation/iteration8b/legacy-analytics.log) и [описание](docs/ITERATION8B_VERIFICATION.md) сохранены.
- SQLite-поиск кириллицы зависит от регистра; телефон не нормализуется. Списки выбора и некоторые связанные списки без отдельной пагинации. История взаимодействий редактируется и не является неизменяемым журналом аудита; email-запись не отправляет письмо. Клиент и автор взаимодействия защищены `PROTECT`, сотрудника с историей следует деактивировать.
- Настройки предназначены для локальной разработки: `DEBUG=True`, локальные хосты, SQLite. Production, нагрузка, полный WCAG-аудит и восстановление среды в новой задаче не проверены. Публичной регистрации, восстановления пароля, ограничения попыток входа, экспорта, платежей, рассылок и фоновых процессов нет.
