## Визуальный отчёт — 8Б

Сохранены режимы all/30d/custom, UTC и определения 8А. Выбранный период показан над отчётом; последние 30 суток — именно 30×24 часа. Карточки отображают total/open/closed/won/lost, исходную Decimal-конверсию и сумму won без ограничения итоговой суммы лимитом одной сделки. Неопределённая конверсия — «Нет данных», недостоверная сумма — сообщение об ошибке, не ноль. Сделки отражают текущие этапы когорты по created_at, взаимодействия — события по occurred_at. Это не история закрытий или фактически полученная выручка.

Горизонтальные диаграммы используют только готовые целочисленные показатели из `crm/analytics.py`. Для этапов знаменатель — total доступных сделок периода; для типов — total доступной истории; для шкал просрочки — текущий total заявок/задач независимо от периода. Чистый `crm/analytics_presentation.py` не импортирует ORM, не меняет отчёт и не пересчитывает деньги/конверсию. Визуальная доля `count/total×100` округляется Decimal HALF_UP до одного знака; CSS получает проверенное ASCII-число 0–100. Из-за округления сумма визуальных долей может отличаться от 100%, исходные количества сохранены.

Нулевой total показывает пустое состояние, нулевые столбцы и неопределённую долю без деления на ноль. Один этап со всеми записями —100%. Неизвестный этап/тип сохраняет предупреждение 8А и таблицу известных значений; полная диаграмма не строится. Неверный период не создаёт ложных графиков; текущая нагрузка остаётся доступна. Повреждённая сумма не препятствует диаграммам корректных количеств и не превращается в частичный денежный итог.

У каждой диаграммы есть заголовок, пояснение знаменателя и видимые значения; таблицы этапов/типов сохранены. Цвета этапов используют палитру Kanban, значения не передаются одним цветом. Новые стили находятся только в `crm/static/crm/analytics.css`, подключаются только на аналитике; глобальный CSS, внешний вид других страниц и Kanban JS не менялись. Анимаций/нового JS/CDN/библиотек нет. Карточки перестраиваются в четыре/два/один столбец по ширине, подписи/таблицы доступны с клавиатуры и без JS.

SQL как в 8А: 5 data queries для валидного отчёта, 2 при неверном периоде (без auth/session); для оформления —0. Проверены 1001 сделка/501 взаимодействие, нет N+1. Chromium 1440/1280/768/375 без JS: данные/доли/геометрия столбцов/фильтры/клавиатура, пустые/один этап/ошибка денег и отсутствие overflow; Kanban JS on/off409 сохранён. Протокол, контрольные числа, известные ограничения — [ITERATION8B_VERIFICATION.md](docs/ITERATION8B_VERIFICATION.md). Формулы 8А не менялись, в ANALYTICS_METRICS добавлено только описание представления.

Новых миграций нет. Рабочая облачная БД по-прежнему ожидает существующую0006: migrate --check на ней exit1, на полностью мигрированной временной SQLite —0. Рабочие данные не изменялись. Для своей копии сначала сделайте backup, примените `python manage.py migrate --noinput` и перезапустите сервер. ## Расчётная основа — 8А (сохранённые определения)

Откройте «Аналитика». Доступ — активным авторизованным сотрудникам; администратор видит все записи по прежним правилам, менеджер — только свои сделки/историю и доступные заявки/задачи. Общая клиентская база не даёт доступ к чужим финансовым показателям. Все ограничения visible_to применяются в SQL до подсчётов/чтения денег, кэша между пользователями нет.

Периоды GET `period=all` (по умолчанию), `30d` (последние 30×24 часа), `custom` с start_date/end_date YYYY-MM-DD. Custom включает начальный день с 00:00 UTC и весь конечный день через границу `<00:00 следующего дня`. Будущие даты и конец раньше начала — ошибка формы; сами события после единого момента расчёта исключаются во всех режимах. У сделок период по **created_at**, у взаимодействий — **occurred_at**. Неверный фильтр не выдаёт ложных нулей и не вызывает 500, текущая нагрузка остаётся доступна.

Показатели: total, пять текущих этапов, open=new+contact+proposal, closed=won+lost; конверсия `won/(won+lost)×100`, Decimal ROUND_HALF_UP до одного знака. Без закрытых — «Нет данных», только lost — 0,0%, только won — 100,0%. Это текущее состояние сделок, **созданных** в период, не результаты закрытия за период: дата закрытия/история этапов не хранятся. Некорректный этап диагностируется отдельно, без скрытой шестой колонки; конверсия в таком случае недоступна.

**«Сумма успешно завершённых сделок»** — только выбранные stage=won; она не равна фактически полученной выручке, платежей в CRM нет. `crm/analytics.py` читает только amount через iterator(chunk_size=500), валидирует конечный Decimal/диапазон/масштаб и суммирует с Decimal precision40. Денежного SQL SUM и float-арифметики в бизнес-логике нет. При обнаруженном повреждении/ошибке конвертации весь денежный итог недоступен, без частичной суммы и 500; техническая причина — в logger crm.analytics, не в HTML.

Предел гарантии SQLite: ORM может округлить исходную raw SQL сумму до проверки (1.234 → Decimal('1.23')). Это реально проверено и не объявляется исправлением исходных денег. Ввод через DealForm и доверенные скрипты Decimal/full_clean остаются обязательными. Формулы, диапазоны и точные гарантии — [ANALYTICS_METRICS.md](docs/ANALYTICS_METRICS.md).

История: общий итог и четыре типа; записи об email не являются отправленными системой письмами. Текущая нагрузка — заявки/задачи и их текущие просрочки независимо от периода, через существующий with_overdue(at), без нового механизма просрочки. Четыре показателя главной не менялись. На валидный отчёт —5 data queries, невалидный фильтр —2, без auth/session; без N+1/новых моделей/фоновых задач/библиотек графиков. Суммирование линейное по доступным успешным сделкам, нагрузочный аудит не проводился.

Контроль: когорта 1 new/1 contact/1 proposal/3 won/2 lost даёт 8 всего, 3 открытых, 5 закрытых, 60,0%; won 0,01+0,02+9999999999,99 =10000000000,02 ₽. Независимые HTTP-контроли, права, ошибки дат/денег и Chromium 1440/1280/768/375 без JS — [протокол 8А](docs/ITERATION8A_VERIFICATION.md).

Новой миграции нет. Рабочая БД не изменялась: в текущей облачной базе ещё ожидает 0006 итерации 7; migrate --check на ней вернул1, на отдельной мигрированной копии —0. Перед запуском этой версии на своей базе сделайте backup и примените существующие миграции командой `python manage.py migrate --noinput`. Скрипт проверки `scripts/verify_iteration8a.py` использует только временную БД и вымышленные записи. Для 8Б расчётная основа готова в пределах описанных гарантий, графики/экспорт/оплаты не добавлены и требуют отдельного задания.

## История взаимодействий — итерация 7

Перед запуском новой версии сохраните резервную копию своей БД и выполните `python manage.py migrate --noinput`. `crm/0006_clientinteraction.py` создаёт только новую таблицу истории с FK/индексами. Старые миграции 0001–0005 не менялись. Проверки проведены на временных БД: существующая рабочая БД не мигрировалась и не заполнялась тестовыми данными. Запуск этой версии на своей базе требует применения 0006.

Откройте «История» → «Добавить взаимодействие» либо соответствующую ссылку в карточке клиента. Выберите клиента, тип, тему, описание и фактическое время UTC. Телефонный звонок/встреча/электронное письмо/комментарий — ручные записи о состоявшемся событии, без реальной отправки, телефонии или автоматического изменения CRM. Прошедшее и текущее время разрешены, будущее — ошибка с сохранением введённого текста; планы оформляйте задачами.

ClientInteraction содержит обязательные client и created_by (оба PROTECT), interaction_type (TextChoices), subject до 200 символов, description до 5000 (необязательное), occurred_at с timezone.now по умолчанию и автоматические created_at/updated_at. Даты timezone-aware, ввод/вывод UTC. Тема обязательна после удаления пробелов. ModelForm задаёт серверную валидацию; прямые ORM/SQL-записи — доверенный путь и должны вызывать full_clean, поскольку save сам не проверяет будущие даты/choices/длину.

| Пользователь | Просмотр и изменение | Удаление |
|---|---|---|
| Активный менеджер | Только собственные записи; автор новой записи устанавливается сервером | Своя — 403, чужая — 404 |
| Активный администратор (is_superuser) | Все записи; создаёт от себя, при редактировании сохраняет первоначального автора | GET подтверждает, POST с CSRF удаляет |

Клиенты по прежним правилам общие для менеджеров, поэтому каждый активный сотрудник может зарегистрировать событие для любого существующего клиента. История ограничивается `ClientInteractionQuerySet.visible_to` до поиска/фильтров/получения объекта. Подмена created_by/created_at/updated_at в POST не меняет автора или служебные даты. Автор при редактировании через форму неизменяем. Анонимные и неактивные пользователи не получают доступ.

| Адрес | Назначение |
|---|---|
| `/interactions/` | Поиск по теме/имени клиента, фильтры типа/клиента, порядок occurred_at/PK, 10 записей на страницу |
| `/interactions/create/` | Создание; `?client=ID` предзаполняет клиента |
| `/interactions/<id>/` | Подробности |
| `/interactions/<id>/edit/` | Редактирование с сохранением автора |
| `/interactions/<id>/delete/` | Подтверждение/удаление администратором |

Параметры списка: q, interaction_type, client, sort=newest/oldest, page. Они сохраняются в пагинации. По умолчанию occurred_at DESC/pk DESC; oldest — ASC/ASC. Некорректный фильтр показывает ошибки формы и пустой результат. Фильтрация/сортировка/пагинация выполняются SQL. Список использует select_related(client,created_by). В карточке клиента максимум 10 последних доступных взаимодействий, тип/тема/время/автор/ссылка; при продолжении — «Вся история этого клиента». SQL LIMIT 11 позволяет узнать только наличие следующей доступной записи без общего count и чужих количеств. Секции заявок/сделок сохранены.

PROTECT запрещает удалять клиента с историей и автора с записями. Попытка удаления клиента выводит понятную ошибку, без 500. Учётную запись сотрудника с историей следует деактивировать; удалить её без отдельного решения о сохранении авторства нельзя. Удаление взаимодействия не удаляет клиента и не затрагивает заявки/задачи/сделки. История не создаёт задач, не меняет этапы, просрочки или автоматизацию.

Ограничения: история редактируемая, не неизменяемый аудит; конкурентные формы истории не имеют версии. Кириллический поиск зависит от SQLite; выбор клиента без отдельной пагинации; нагрузка, другие браузеры, полный WCAG и production не проверены. Два составных индекса обоснованы запросами по автору/времени и клиенту/времени. Проверенный рендер списка — 3 data queries, карточки клиента — 4 вместе с прежними секциями, без auth/session; N+1 нет. Стили и Kanban JS не изменены, новых зависимостей нет.

Исторические проверки, миграция с копии 6C, команды и ручной чек-лист — [отчёт итерации 7](docs/ITERATION7_VERIFICATION.md). Базовые 205 тестов в той итерации не менялись, в том числе CAS/no-op/409 и Decimal. Автоматизация, модели ClientRequest/Task/Deal и логика 6C сохранены. Расчётная аналитика добавлена в 8А, визуализация 8Б не начата.

## Стабилизация 6C: версия карточки и деньги — историческое состояние

Обычная форма и `crm/static/crm/kanban.js` передают в прежний POST смены этапа обязательные `stage` и `expected_updated_at` — полный ISO timestamp карточки, включая микросекунды и часовой пояс. CSRF и явный Accept: application/json сохранены. Отсутствующая/неверная версия даёт 400, устаревшая — 409. При JSON 409 клиент показывает сообщение/обновление, оставляет старый DOM и останавливает дальнейший DnD до перечитывания. Без JS отображается страница конфликта со ссылкой на доску. После обновления DOM получает свежие версии; внешний next игнорируется.

Условие записи выполняется в одном SQL UPDATE: pk, assigned_to менеджера (visible_to), предыдущий stage и ожидаемый updated_at. Если строка больше не соответствует, она не обновляется: при потере доступа/удалении — общий 404, при новой версии доступной сделки — 409. Это compare-and-swap без select_for_update и без новой схемы. Новая дата строго больше версии, даже при совпадении/откате часов; A→B→A не делает старую карточку актуальной. Повтор POST со старой версией после реального перехода — 409; актуальный same-stage — 200/HTML redirect без UPDATE и смены даты. Это не ключ идемпотентности HTTP.

Загрузка колонок не менялась: серверные экранированные partials, scoped counts, SQL LIMIT 20, select_related и created_at DESC/pk DESC. Доска — 6 data queries, успешный JSON-переход — 5, актуальный JSON no-op — 4 (добавлена проверка доступности/версии в момент no-op); auth/session не включены. Снимок всех колонок под нагрузкой не гарантируется. Защита версии относится к endpoint смены этапа Kanban; обычный CRUD редактирования сделки не получил общей блокировки конкурентных форм. Прямые update/SQL обязаны обновлять updated_at, иначе проверку версии можно обойти; это доверенный внутренний путь, не публичный контракт.

Денежные формы используют Decimal(12,2), диапазон 0.01–9999999999.99; float в расчётах приложения не используется. БД дополнительно гарантирует только amount > 0. В SQLite прямой `Deal.objects.create(amount=Decimal('10000000000.00'), ...)` сохраняет значение, превышающее max_digits; `refresh_from_db()` затем вызывает decimal.InvalidOperation. Это воспроизводит новый изолированный тест, нормальная ModelForm отклоняет сумму. SQLite также не гарантирует два знака и точность прямого SQL/ORM-ввода. Правило MVP: пользовательские записи — через валидированную форму; доверенные импорты/скрипты обязаны вызывать full_clean перед save и подавать Decimal из строк. Для будущей аналитики сначала проверять диапазон/масштаб исходных сумм, считать по согласованным правилам Decimal, не обещать точный денежный SUM SQLite; выбор СУБД и формул — работа этапа 8.

Осознанные ограничения MVP относительно ТЗ: FR-06 допускает задачу для заявки или сделки, но Task сейчас связан **только с заявкой**. Задачи сделок не реализованы; FR-06 выполнен частично, ТЗ молча не изменяется. Вместо запланированного Bootstrap сохранён собственный локальный CSS по решениям прежних итераций; это документированное отклонение стека интерфейса, зависимость Bootstrap не подключена.

Проверки и точные изменения старых тестов: [отчёт 6C](docs/STAGE6C_VERIFICATION.md). Скрипт HTTP/Chromium сохранён в `scripts/verify_stage6c.py`; воспроизводимые команды и ограничения браузерной проверки — в отчёте. Миграции/модели/пользовательские данные не менялись, стабильная версия сохранена тегом `iteration-6b2`.

## Локальный запуск

Нужен Python 3.12 (проверено на 3.12.14). Команды выполняются из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
python manage.py migrate --noinput
python manage.py runserver 127.0.0.1:8000
```

Откройте `/login/` на локальном сервере. Главная `/` доступна только после входа. Неверные данные показывают сообщение об ошибке; неактивные пользователи войти не могут. Кнопка «Выйти» отправляет POST с CSRF-токеном. GET `/logout/` возвращает 405 и сохраняет сессию. Внешний адрес в `next` отклоняется стандартным `LoginView`.

В новом терминале снова активируйте окружение и задайте `DJANGO_SECRET_KEY`; для сохранения сессий используйте один и тот же ключ через безопасное локальное окружение. Не добавляйте его в Git.

## Администратор и менеджер

В активированном окружении с заданным ключом выполните:

```bash
python manage.py createsuperuser
```

Введите собственные локальные данные интерактивно. Войдите через `/login/` и откройте «Управление пользователями» или войдите напрямую через `/admin/`.

В Admin откройте «Пользователи» → «Добавить пользователя», задайте логин и пароль менеджера. ## Задачи

После обновления примените `python manage.py migrate --noinput`. Миграция `crm/0003_task.py` добавляет таблицу задач; предыдущие модели не перестраиваются. Перед обновлением рабочей базы сделайте резервную копию.

`Task` содержит id, обязательную заявку `request` (`ClientRequest`, `PROTECT`), название до 255 символов (ручной ввод — 200), необязательное описание до 5000 символов, ответственного пользователя (`SET_NULL`), статус, необязательный срок `due_at`, служебную дату завершения `completed_at`, неизменяемый в форме признак `is_automatic` и автоматические даты создания/изменения. Логика в `Task.save()` централизованно устанавливает дату завершения, сохраняет её при повторном сохранении выполненной задачи, очищает при возобновлении и устанавливает заново при повторном завершении. `completed_at` не редактируется формой и не принимается из POST. Частичное сохранение через `save(update_fields=...)` также поддерживается. Для изменения статуса через ORM используйте `save()`: `QuerySet.update()`, `bulk_update()` и `bulk_create()` обходят эту логику.

Администратор видит все задачи и может создавать, редактировать, менять статус и удалять их. В форме он обязан выбрать активного ответственного, совпадающего с текущим ответственным заявки. Если у заявки нет активного ответственного, сначала измените заявку. Несогласованное назначение отклоняется при создании и редактировании, поэтому администратор должен исправить его перед сохранением существующей задачи.

Старый менеджер теряет доступ к ним, новый также не видит и не редактирует чужие задачи. Администратор видит такие задачи и должен вручную привести ответственного в соответствие с заявкой через редактирование задачи. После этого новый менеджер получает доступ. В карточке заявки список задач ограничен теми же правами; ссылки, названия и результаты поиска чужих заявок не раскрываются.

Ограничения: общие ограничения SQLite и локальной среды сохранены; списки выбора заявок/сотрудников и задачи в карточке заявки без отдельной пагинации. История переходов статусов и переназначений не ведётся. Прямой ORM save не запускает полную валидацию формы/модели; серверные проверки назначения выполняет TaskForm. Нагрузочные и конкурентные изменения не проверялись.

## Автоматизация и просрочка — историческое описание этапа 5

Примените `python manage.py migrate --noinput` после обновления. Миграция `crm/0004_task_is_automatic_alter_task_title_and_more.py` добавляет признак происхождения и частичное уникальное ограничение, расширяет название Task до 255. Все прежние задачи получают `is_automatic=False`; старые заявки не получают новых задач при миграции.

**Событие:** успешный POST создания заявки через `/requests/create/`. `crm/services.py:create_request_with_task(form)` сохраняет валидную форму и вызывает `ensure_automatic_task(linked_request)` внутри `transaction.atomic()`. Ошибка операции откатывает обе записи, сообщение об успехе не выдаётся. Интерфейс сохраняет введённые поля, показывает «Данные не сохранены» и предлагает повторить; техническая ошибка записывается в серверный журнал.

Автоматическая задача получает название `Обработать заявку №ID: название заявки`, статус `new`, связь с созданной заявкой и того же активного ответственного. Срок копируется из заявки; при отсутствии срока вычисляется через `timezone.now() + 24 часа` непосредственно в операции создания. Поле Task.title расширено до 255 для полного префикса и 200-символьного названия заявки без обрезания; ручная форма сохраняет лимит 200, форма существующей автоматической задачи допускает 255. Признак происхождения нельзя подставить через POST; автоматическую задачу нельзя перенести к другой заявке через форму, чтобы не нарушить её идентичность.

**Идемпотентность:** сервис использует `get_or_create`, а БД ограничивает число задач с `is_automatic=True` для одной заявки через `UniqueConstraint(condition=...)`. Повторный вызов `ensure_automatic_task` возвращает ту же задачу, не меняет её название, назначение, срок или выполненный статус. Ручные задачи не ограничены этим правилом. Идемпотентность относится к существующему ID заявки, а не к повторной отправке формы создания: два независимых POST могут создать две разные заявки, каждая со своей задачей. После явного удаления автоматической задачи администратором отдельный вызов сервиса может создать замену; редактирование заявки само сервис не вызывает.

Автоматизация не подключена к model.save, Signals, миграциям или Django Admin. Прямой ORM и редактирование заявки не создают задач. Названия, сроки и ответственные существующих задач автоматически не синхронизируются при изменении заявки. Правило ручного исправления назначения администратором сохранено, включая изоляцию обоих менеджеров в списках, прямых URL и показателях.

**Просрочка:** `due_at` должен быть заполнен и строго меньше текущего aware-времени. Для Task допустимы только статусы `new`/`in_progress`; для ClientRequest — также только `new`/`in_progress`. Выполненные задачи, завершённые/отменённые заявки, записи без срока и срок ровно сейчас не считаются текущими просроченными. Просрочка задачи и заявки независима. Она не записывается как статус и не меняет БД. Завершение задачи сохраняет прежнюю логику completed_at и убирает отметку; возобновление после срока возвращает отметку, но не меняет статус заявки.

Общая `with_overdue(at)` вычисляет SQL-признак для фильтров, таблиц и счётчиков; `is_overdue` — текущее состояние карточки. Обе реализации используют общие OPEN_STATUSES, их эквивалентность проверяется на контролируемых граничных датах. В списках `/tasks/` и `/requests/` доступны `overdue=yes` и `overdue=no`, совместимые с `q`, `status`, `sort` и `page`. `no` включает также записи без срока и завершённые. Параметры сохраняются в пагинации. Неизвестное значение overdue игнорируется. Просрочка выделяется текстом «Просрочена».

**Главная:** четыре показателя — доступные заявки, задачи, просроченные заявки и задачи. Для менеджера заявки ограничены assigned_to, задачи — совпадением ответственного задачи и заявки. Для активного суперпользователя учитываются все записи, включая неназначенные. Используются реальные агрегаты БД и один момент времени на расчёт всех четырёх показателей. Фильтры и счётчики не раскрывают чужие данные. Значения обновляются при загрузке страницы, без polling, cron и фоновых процессов.

Ограничения автоматизации: SQLite не блокирует строку через select_for_update; конкурентная запись может вернуть ошибку блокировки и потребовать повторить операцию. Частичный уникальный индекс предотвращает дубли автоматической задачи, но конкурентная нагрузка и другая СУБД не проверялись. Массовые ORM-обновления обходят Task.save; прямые вызовы внутренних сервисов требуют доверенного вызывающего кода и проверки его полномочий. Статусы, сроки и назначения существующих задач не синхронизируются автоматически. Сохраняются ограничения локальной среды и поиска SQLite. Email, фоновые задания, drag-and-drop и полноценная аналитика не добавлены.

Откройте «Сделки» → «Добавить сделку», выберите клиента, введите название и положительную сумму; описание и планируемую дату можно не указывать. Дата закрытия — календарная дата без времени, прошедшая дата допускается. После сохранения показывается сообщение и карточка. Поиск `q` ищет подстроку в названии или имени клиента, `stage` фильтрует этап, `sort=newest/oldest` задаёт порядок по дате создания с pk как вторым ключом. Пагинация по 10 сохраняет параметры. Неверный номер страницы — 404; неизвестные этап/сортировка фильтра игнорируются. Для кириллицы сохраняется ограничение регистра SQLite.

Менеджер создаёт сделку на себя независимо от assigned_to в POST, видит/редактирует только свои записи и не может менять ответственного. Чужая карточка/редактирование — 404; удаление менеджеру — 403. Администратор видит все записи, назначает только активного пользователя, переназначает и удаляет. После удаления пользователя сделка остаётся без ответственного и доступна администратору для переназначения; при сохранении формы он обязан выбрать активного сотрудника. Сделки не наследуют ответственного из заявки, поскольку связи с заявкой нет.

Карточка клиента содержит только доступные пользователю сделки, без чужих ссылок и названий. Самих клиентов обе роли видят по прежним правилам. Клиент со сделками защищён от удаления: выводится понятное сообщение и данные сохраняются. Удаление сделки не удаляет клиента. Изменения — только POST с CSRF, GET подтверждения не меняет БД, PUT/DELETE не поддерживаются. Drag-and-drop, графики, email и новые фоновые процессы не добавлены.

Ограничения: прямой ORM save не вызывает full_clean; проверки точности/длины и активного назначения относятся к ModelForm, положительная сумма дополнительно ограничена БД. Списки выбора клиентов/пользователей и сделки в карточке клиента без отдельной пагинации. Production/нагрузка/конкурентность не проверены.

## Воронка продаж — историческое описание 6Б.1

Откройте «Сделки» → «Воронка продаж» (`/deals/kanban/`). Альтернативный список `/deals/` сохранён; ссылка на доску есть и в карточке сделки. Используется та же Deal, без новых таблиц, копий этапа и миграций. Колонки и списки выбора строятся из Deal.Stage.choices в порядке new, contact, proposal, won, lost.

Заголовок каждой колонки содержит полное число доступных сделок. Показываются максимум 20 карточек, отсортированных по created_at DESC, pk DESC. Ограничение выполняется SQL LIMIT, а не загрузкой всех записей в Python. При количестве больше 20 ссылка «Посмотреть все» открывает `/deals/?stage=...`. Нулевой этап показывает сообщение. Одна группировка Count и пять ограниченных выборок с select_related дают шесть запросов за данные доски независимо от числа карточек (без запросов сессии/аутентификации). Денежных SQL-агрегатов нет.

Карточки показывают ID/название со ссылкой, клиента, индивидуальную сумму в рублях с двумя знаками, ответственного и заполненную плановую дату. Администратору доступны все сделки, включая неназначенные; менеджеру только assigned_to=self. Одинаковый DealQuerySet.visible_to применяется до подсчётов и выборок, поэтому чужие числа, названия и ссылки не раскрываются.

В карточке выберите этап и нажмите «Переместить». POST `/deals/<id>/change-stage/` использует CSRF и DealStageForm с существующими TextChoices. Авторизованный GET возвращает 405; чужая/несуществующая сделка на POST — 404; неверный/отсутствующий stage — 400 с сообщением и формой исправления, без изменения БД. Успех перенаправляет на фиксированный `/deals/kanban/` и показывает сообщение. Параметры внешнего редиректа игнорируются. Можно переходить между любыми этапами. При действительном изменении сохраняются только stage/updated_at; created_at, клиент, сумма, ответственный и другие поля не изменяются, даже при их подмене в POST. Повтор того же этапа — безопасный no-op без записи и изменения updated_at. Новые сделки, заявки и задачи endpoint не создаёт.

На 1440/1280 px видны все пять колонок; на 768/375 px прокручивается область доски, а не вся страница. До последнего этапа можно дойти прокруткой. Область фокусируется Tab и прокручивается стрелками, формы имеют связанные уникальные подписи/ID и именованные кнопки; выбор этапа и Enter работают без JavaScript. Длинный текст переносится внутри карточек. В 6Б.1 перетаскивания ещё не было; возможности 6Б.2 описаны ниже. Библиотек перетаскивания, REST API и WebSocket нет.

Ограничения: не более 100 карточек на всей доске, полные записи доступны через список. У больших колонок доска может быть высокой; внутренней вертикальной пагинации нет. Счётчики и карточки читаются отдельными запросами, при параллельных изменениях возможен сдвиг между ними; конкурентность/нагрузка не проверены, история этапов и конфликтное редактирование не реализованы. Существующие ограничения SQLite и локального размещения сохранены.

## Drag-and-drop и проверка 6Б.2 — историческое состояние

Локальный `crm/static/crm/kanban.js` использует стандартный HTML Drag and Drop API, fetch и делегирование событий. Перетащите карточку за область «Перетащить» в другую колонку. Формы выбора этапа всегда доступны, в том числе с клавиатуры, без JS и на сенсорном устройстве; жесты прокрутки не перехватываются. Декоративная анимация учитывает prefers-reduced-motion. Уведомления имеют aria-live, видны при прокрутке и скрываются кнопкой.

Используется прежний `POST /deals/<id>/change-stage/`: форма передаёт stage, CSRF — скрытое поле. JS передаёт stage в URLSearchParams, `Accept: application/json`, `X-CSRFToken` из формы и same-origin cookies. HTML-запросы сохраняют redirect на доску. Только явно запрошенный JSON содержит success/deal_id/stage/message и columns с stage/count/html. Ошибки JSON: 400 — этап, 401 — сессия, 403 — CSRF, 404 — чужой/несуществующий объект, 405 — метод, 500 — непредвиденный отказ без внутренних данных. CSRF_FAILURE_VIEW специализирует только JSON смены этапа; остальные страницы используют стандартный обработчик Django.

Оба режима используют одну проверку прав visible_to и DealStageForm; меняются только stage/updated_at, повтор этапа не сохраняет запись. Общий `crm/kanban.py` загружает полные счётчики и ограниченные SQL LIMIT 20 карточки с select_related, сортировкой created_at DESC/pk DESC. `_kanban_card.html` и `_kanban_column.html` используются и при открытии доски, и для ответа JSON. Сервер перечитывает только исходную и целевую колонки: следующая карточка заполняет освободившееся место, в полной целевой колонке остаётся максимум 20. Измерено без запросов аутентификации: полная доска — 6 запросов; JSON-переход — 5 (объект, UPDATE, count, две колонки), серверный no-op — 3. Финансовых агрегатов/N+1 нет.

До подтверждения карточка остаётся на месте. На время запроса блокируются новые перетаскивания и отправка форм доски, обычные ссылки доступны. Одна операция на всю доску предотвращает гонки ответов двух колонок. После успеха заменяются только серверные фрагменты двух колонок, новые карточки сразу работают; полная страница не перезагружается. Пользовательский текст выводится через textContent либо экранирование Django, произвольный HTML клиента не вставляется. На том же этапе клиент не отправляет запрос.

Таймаут — 15 секунд. Ошибка 400 допускает исправление и повтор. При сетевом сбое, таймауте, 401/403/404/500 или неожиданном ответе дальнейшее перетаскивание останавливается до обновления доски: сервер мог уже сохранить этап либо права могли измениться. Доступна ссылка «Обновить доску»; формы/навигация остаются доступны после завершения запроса. HTML страницы входа не вставляется в доску.
