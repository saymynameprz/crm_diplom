# Дипломная CRM

Итерация 6Б.1: к существующим клиентам, заявкам, задачам и сделкам добавлена Kanban-доска с безопасной серверной сменой этапов. Доска и счётчики ограничены правами пользователя, формы работают без JavaScript. Drag-and-drop и другие дополнительные модули не реализованы.

## Локальный запуск

Нужен Python 3.12 (проверено на 3.12.14). Команды выполняются из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
python manage.py migrate --noinput
python manage.py runserver 127.0.0.1:8000
```

Откройте `/login/` на локальном сервере. Главная `/` доступна только после входа. Неверные данные показывают сообщение об ошибке; неактивные пользователи войти не могут. Кнопка «Выйти» отправляет POST с CSRF-токеном. GET `/logout/` возвращает 405 и сохраняет сессию. Внешний адрес в `next` отклоняется стандартным `LoginView`.

В новом терминале снова активируйте окружение и задайте `DJANGO_SECRET_KEY`; для сохранения сессий используйте один и тот же ключ через безопасное локальное окружение. Не добавляйте его в Git.

## Администратор и менеджер

В активированном окружении с заданным ключом выполните:

```bash
python manage.py createsuperuser
```

Введите собственные локальные данные интерактивно. Войдите через `/login/` и откройте «Управление пользователями» или войдите напрямую через `/admin/`.

В Admin откройте «Пользователи» → «Добавить пользователя», задайте логин и пароль менеджера. В карточке пользователя оставьте «Активный» включённым, «Статус персонала» и «Статус суперпользователя» — выключенными; сохраните. При необходимости укажите имя и фамилию. Публичной регистрации нет, готовые учётные записи не поставляются.

Доступ к Admin разрешён только активным `is_superuser=True`, независимо от `is_staff`. Менеджер с ошибочно включённым `is_staff` также не получит доступ. Используются встроенная модель `User` и стандартное управление пользователями Django; собственных таблиц ролей и миграций нет.

Настройки предназначены только для разработки: `DEBUG=True`, разрешены локальные хосты, SQLite, язык интерфейса русский, хранение времени UTC. Для production требуется отдельная конфигурация.

## Клиенты

После обновления проекта выполните `python manage.py migrate --noinput` в активном окружении с заданным ключом. Миграция `crm/0001_initial.py` добавляет таблицу клиентов; существующие таблицы пользователей не перестраиваются. Перед миграцией своей рабочей базы сделайте резервную копию.

| Страница | Назначение |
|---|---|
| `/clients/` | Список, поиск, фильтр и сортировка |
| `/clients/create/` | Создание |
| `/clients/<id>/` | Карточка |
| `/clients/<id>/edit/` | Редактирование |
| `/clients/<id>/delete/` | GET — подтверждение, POST — удаление |

Войдите, выберите «Клиенты» → «Добавить клиента», заполните имя и нажмите «Сохранить». Пустое имя и имя из пробелов не принимаются, пробелы по краям убираются. Телефон, email, организация и примечание необязательны. Email проверяется стандартным валидатором Django; строгого формата телефона нет. Ограничения формы: имя и организация — 200 символов, телефон — 50, email — 254, примечание — 5000. Повторяющиеся имена и контакты разрешены.

Обе роли видят общую базу клиентов и могут добавлять и редактировать записи. Удаление доступно только активному суперпользователю: откройте карточку → «Удалить» → подтвердите кнопкой. GET не удаляет запись, менеджеру GET и POST удаления возвращают 403. Анонимные запросы перенаправляются на вход; изменяющие формы защищены CSRF.

Поиск `q` ищет подстроку в имени, телефоне, email или организации. Фильтр `company=yes/no` выбирает наличие/отсутствие организации. `sort=newest/oldest` задаёт порядок по дате создания, по умолчанию новые сначала. На странице 10 записей, параметры сохраняются в ссылках пагинации. Неверный номер страницы возвращает 404. Пустой список и отсутствие совпадений показывают отдельные сообщения. После сохранения и удаления показывается уведомление.

Ограничения поиска: SQLite `icontains` не обеспечивает регистронезависимость кириллицы; для кириллических имён учитывайте регистр. Телефон ищется как сохранённая строка, без нормализации пунктуации. Разделения клиентской базы по менеджерам нет: это не предусмотрено заданием. Используйте только вымышленные данные для демонстрации.

## Заявки

После обновления выполните `python manage.py migrate --noinput`: миграция `crm/0002_clientrequest.py` добавляет `ClientRequest`. Перед изменением рабочей базы сохраните её резервную копию.

Модель содержит обязательного клиента (`ForeignKey`, `PROTECT`), название до 200 символов, необязательное описание до 5000 символов, статус (`TextChoices`), ответственного пользователя (`SET_NULL`), необязательный срок обработки и автоматические даты создания/изменения. Удаление пользователя сохраняет заявку с пустым ответственным; такую заявку видит администратор и может назначить активному сотруднику. Сохранить форму администратора без активного ответственного нельзя, в том числе при редактировании заявки удалённого или деактивированного сотрудника.

Новая заявка через CRM всегда создаётся только в `new`: в форме создания поля статуса нет, подставленные POST-значения игнорируются сервером. Статус меняется уже через редактирование.

Статусы: `new` — «Новая» (по умолчанию), `in_progress` — «В работе», `completed` — «Завершена», `cancelled` — «Отменена». Статус показан текстом и цветом. Переходы между всеми четырьмя статусами разрешены; история переходов не ведётся; автоматическое создание задачи запускается только при создании заявки через CRM.

| Адрес | Назначение |
|---|---|
| `/requests/` | Таблица доступных заявок |
| `/requests/create/` | Создание |
| `/requests/<id>/` | Карточка с переходом к клиенту |
| `/requests/<id>/edit/` | Изменение |
| `/requests/<id>/delete/` | GET — подтверждение, POST — удаление администратором |

Войдите → «Заявки» → «Добавить заявку», выберите существующего клиента, введите название, при необходимости описание и срок, сохраните. Администратор выбирает любого активного ответственного пользователя. Менеджер назначается самому себе, поля переназначения у него нет; подставленный `assigned_to` в POST игнорируется. Менеджер видит и редактирует только свои заявки; чужая карточка или форма возвращает 404, удаление запрещено с кодом 403. Администратор видит и изменяет все заявки, может переназначать и удалять. Изменения отправляются только через POST с CSRF; GET не изменяет данные, PUT/DELETE не поддерживаются.

В карточке клиента отображаются связанные заявки: администратору все, менеджеру только его собственные. Если доступных заявок нет, показывается сообщение. При попытке удалить клиента со связанными заявками выводится понятная ошибка без потери данных. Права на создание и редактирование самих клиентов остаются общими для обеих ролей.

Список поддерживает поиск по названию (`q`), фильтр статуса (`status`), сортировку `newest/oldest` по дате создания и пагинацию по 10 записей (`page`). Параметры сохраняются при переходах страниц. Неизвестные статус/сортировка фильтра не применяются, используется порядок по умолчанию; неверная страница — 404. Ограничение SQLite для регистра кириллицы действует и здесь.

Срок вводится и показывается в UTC с точностью до минуты; оформление календарного поля зависит от языка браузера. Разрешены пустой срок и прошедшая дата; текущая просрочка вычисляется по правилам ниже. Даты хранятся с учётом часового пояса. При неверном статусе на редактировании, клиенте, ответственном или формате даты запись не сохраняется; форма выводит ошибки и сохраняет введённые данные. Как и для клиентов, прямой ORM save сам не вызывает full_clean — проверки относятся к пользовательской форме.

## Задачи

После обновления примените `python manage.py migrate --noinput`. Миграция `crm/0003_task.py` добавляет таблицу задач; предыдущие модели не перестраиваются. Перед обновлением рабочей базы сделайте резервную копию.

`Task` содержит id, обязательную заявку `request` (`ClientRequest`, `PROTECT`), название до 255 символов (ручной ввод — 200), необязательное описание до 5000 символов, ответственного пользователя (`SET_NULL`), статус, необязательный срок `due_at`, служебную дату завершения `completed_at`, неизменяемый в форме признак `is_automatic` и автоматические даты создания/изменения. Удаление пользователя сохраняет задачу; удаление заявки с задачами блокируется понятным сообщением без потери данных.

Статусы `TextChoices`: `new` — «Новая» (по умолчанию), `in_progress` — «В работе», `completed` — «Выполнена». Логика в `Task.save()` централизованно устанавливает дату завершения, сохраняет её при повторном сохранении выполненной задачи, очищает при возобновлении и устанавливает заново при повторном завершении. `completed_at` не редактируется формой и не принимается из POST. Частичное сохранение через `save(update_fields=...)` также поддерживается. Для изменения статуса через ORM используйте `save()`: `QuerySet.update()`, `bulk_update()` и `bulk_create()` обходят эту логику.

| Адрес | Назначение |
|---|---|
| `/tasks/` | Список доступных задач |
| `/tasks/create/` | Создание задачи для существующей заявки |
| `/tasks/<id>/` | Карточка с ответственным, сроком и датой завершения |
| `/tasks/<id>/edit/` | Редактирование и смена статуса |
| `/tasks/<id>/delete/` | GET — подтверждение, POST — удаление администратором |

Откройте «Задачи» → «Добавить задачу», выберите заявку, введите название и сохраните. Доступны поиск по названию (`q`), фильтр трёх статусов (`status`), порядок по дате создания (`sort=newest/oldest`) и пагинация по 10 (`page`) с сохранением параметров. Пустой список и отсутствие результатов показывают сообщения. Срок необязателен, прошедшие даты разрешены; ввод и отображение — UTC с точностью до минуты. Просрочка вычисляется без изменения статуса; автоматическая задача появляется при создании новой заявки через CRM, ручные задачи создаются независимо.

Администратор видит все задачи и может создавать, редактировать, менять статус и удалять их. В форме он обязан выбрать активного ответственного, совпадающего с текущим ответственным заявки. Если у заявки нет активного ответственного, сначала измените заявку. Несогласованное назначение отклоняется при создании и редактировании, поэтому администратор должен исправить его перед сохранением существующей задачи.

Менеджер создаёт задачи только для своих заявок; сервер назначает его самого независимо от `assigned_to` в POST. Он видит и редактирует задачу только при одновременном совпадении ответственного задачи и ответственного заявки с текущим пользователем. Поле ответственного и дата завершения недоступны для редактирования. Чужая задача возвращает 404, удаление менеджеру запрещено с кодом 403. Администратор удаляет задачу только POST-формой с CSRF; GET безопасен, PUT/DELETE не поддерживаются.

Администратору на форме редактирования заявки показывается заметное пояснение о необходимости ручного переназначения существующих задач.

**Временное правило переназначения:** при смене ответственного заявки прежние задачи автоматически не меняют ответственного. Старый менеджер теряет доступ к ним, новый также не видит и не редактирует чужие задачи. Администратор видит такие задачи и должен вручную привести ответственного в соответствие с заявкой через редактирование задачи. После этого новый менеджер получает доступ. В карточке заявки список задач ограничен теми же правами; ссылки, названия и результаты поиска чужих заявок не раскрываются.

Ограничения: общие ограничения SQLite и локальной среды сохранены; списки выбора заявок/сотрудников и задачи в карточке заявки без отдельной пагинации. История переходов статусов и переназначений не ведётся. Прямой ORM save не запускает полную валидацию формы/модели; серверные проверки назначения выполняет TaskForm. Нагрузочные и конкурентные изменения не проверялись.

## Автоматизация и просрочка

Примените `python manage.py migrate --noinput` после обновления. Миграция `crm/0004_task_is_automatic_alter_task_title_and_more.py` добавляет признак происхождения и частичное уникальное ограничение, расширяет название Task до 255. Все прежние задачи получают `is_automatic=False`; старые заявки не получают новых задач при миграции.

**Событие:** успешный POST создания заявки через `/requests/create/`. `crm/services.py:create_request_with_task(form)` сохраняет валидную форму и вызывает `ensure_automatic_task(linked_request)` внутри `transaction.atomic()`. Ошибка операции откатывает обе записи, сообщение об успехе не выдаётся. Интерфейс сохраняет введённые поля, показывает «Данные не сохранены» и предлагает повторить; техническая ошибка записывается в серверный журнал.

Автоматическая задача получает название `Обработать заявку №ID: название заявки`, статус `new`, связь с созданной заявкой и того же активного ответственного. Срок копируется из заявки; при отсутствии срока вычисляется через `timezone.now() + 24 часа` непосредственно в операции создания. Поле Task.title расширено до 255 для полного префикса и 200-символьного названия заявки без обрезания; ручная форма сохраняет лимит 200, форма существующей автоматической задачи допускает 255. Признак происхождения нельзя подставить через POST; автоматическую задачу нельзя перенести к другой заявке через форму, чтобы не нарушить её идентичность.

**Идемпотентность:** сервис использует `get_or_create`, а БД ограничивает число задач с `is_automatic=True` для одной заявки через `UniqueConstraint(condition=...)`. Повторный вызов `ensure_automatic_task` возвращает ту же задачу, не меняет её название, назначение, срок или выполненный статус. Ручные задачи не ограничены этим правилом. Идемпотентность относится к существующему ID заявки, а не к повторной отправке формы создания: два независимых POST могут создать две разные заявки, каждая со своей задачей. После явного удаления автоматической задачи администратором отдельный вызов сервиса может создать замену; редактирование заявки само сервис не вызывает.

Автоматизация не подключена к model.save, Signals, миграциям или Django Admin. Прямой ORM и редактирование заявки не создают задач. Названия, сроки и ответственные существующих задач автоматически не синхронизируются при изменении заявки. Правило ручного исправления назначения администратором сохранено, включая изоляцию обоих менеджеров в списках, прямых URL и показателях.

**Просрочка:** `due_at` должен быть заполнен и строго меньше текущего aware-времени. Для Task допустимы только статусы `new`/`in_progress`; для ClientRequest — также только `new`/`in_progress`. Выполненные задачи, завершённые/отменённые заявки, записи без срока и срок ровно сейчас не считаются текущими просроченными. Просрочка задачи и заявки независима. Она не записывается как статус и не меняет БД. Завершение задачи сохраняет прежнюю логику completed_at и убирает отметку; возобновление после срока возвращает отметку, но не меняет статус заявки.

Общая `with_overdue(at)` вычисляет SQL-признак для фильтров, таблиц и счётчиков; `is_overdue` — текущее состояние карточки. Обе реализации используют общие OPEN_STATUSES, их эквивалентность проверяется на контролируемых граничных датах. В списках `/tasks/` и `/requests/` доступны `overdue=yes` и `overdue=no`, совместимые с `q`, `status`, `sort` и `page`. `no` включает также записи без срока и завершённые. Параметры сохраняются в пагинации. Неизвестное значение overdue игнорируется. Просрочка выделяется текстом «Просрочена».

**Главная:** четыре показателя — доступные заявки, задачи, просроченные заявки и задачи. Для менеджера заявки ограничены assigned_to, задачи — совпадением ответственного задачи и заявки. Для активного суперпользователя учитываются все записи, включая неназначенные. Используются реальные агрегаты БД и один момент времени на расчёт всех четырёх показателей. Фильтры и счётчики не раскрывают чужие данные. Значения обновляются при загрузке страницы, без polling, cron и фоновых процессов.

Ограничения автоматизации: SQLite не блокирует строку через select_for_update; конкурентная запись может вернуть ошибку блокировки и потребовать повторить операцию. Частичный уникальный индекс предотвращает дубли автоматической задачи, но конкурентная нагрузка и другая СУБД не проверялись. Массовые ORM-обновления обходят Task.save; прямые вызовы внутренних сервисов требуют доверенного вызывающего кода и проверки его полномочий. Статусы, сроки и назначения существующих задач не синхронизируются автоматически. Сохраняются ограничения локальной среды и поиска SQLite. Email, фоновые задания, drag-and-drop и полноценная аналитика не добавлены.

## Сделки (6А)

Примените `python manage.py migrate --noinput` после обновления: `crm/0005_deal.py` добавляет Deal и ограничение положительной суммы. Предыдущие таблицы не перестраиваются. Перед миграцией рабочей базы сохраните её резервную копию.

Поля Deal: id, client (`PROTECT`), title (200), необязательное description (5000), amount (`DecimalField(max_digits=12, decimal_places=2)`), stage (`TextChoices`), assigned_to (`SET_NULL`), необязательная expected_close_date (`DateField`), created_at/updated_at. Связь непосредственно с клиентом позволяет вести сделку независимо от регистрации заявки; обязательной связи с ClientRequest нет.

Сумма обязательна, в рублях: от 0.01 до 9999999999.99, максимум два десятичных знака. На сервере ModelForm/DecimalValidator проверяют формат, число цифр и точность; MinValueValidator(Decimal('0.01')) и DB CheckConstraint(amount>0) запрещают неположительные суммы. Ввод через стандартное числовое поле, пример POST — `1234.56`; отображение локализовано с двумя знаками и символом ₽. При ошибке запись не сохраняется, введённый текст формы остаётся для исправления. В коде финансовые значения не переводятся во float. Конвертации валют нет. SQL-вычисления с деньгами на SQLite не являются подтверждённой production-гарантией точности: финансовая арифметика и аналитика вне этой итерации, для них нужна отдельная оценка СУБД.

Этапы: `new` — «Новая», `contact` — «Контакт установлен», `proposal` — «Коммерческое предложение», `won` — «Успешно завершена», `lost` — «Проиграна». При создании поле этапа отсутствует, любое POST-stage игнорируется, сервер устанавливает new. При редактировании разрешены все пять этапов и переходы между ними, неверный этап отклоняется. Истории этапов и автоматических действий нет.

| Адрес | Назначение |
|---|---|
| `/deals/` | Доступные сделки, поиск, фильтр, сортировка |
| `/deals/create/` | Новая сделка |
| `/deals/<id>/` | Карточка с суммой, этапом, ответственным, датой и клиентом |
| `/deals/<id>/edit/` | Редактирование суммы/этапа и других полей |
| `/deals/<id>/delete/` | GET — подтверждение, POST — удаление администратором |

Откройте «Сделки» → «Добавить сделку», выберите клиента, введите название и положительную сумму; описание и планируемую дату можно не указывать. Дата закрытия — календарная дата без времени, прошедшая дата допускается. После сохранения показывается сообщение и карточка. Поиск `q` ищет подстроку в названии или имени клиента, `stage` фильтрует этап, `sort=newest/oldest` задаёт порядок по дате создания с pk как вторым ключом. Пагинация по 10 сохраняет параметры. Неверный номер страницы — 404; неизвестные этап/сортировка фильтра игнорируются. Для кириллицы сохраняется ограничение регистра SQLite.

Менеджер создаёт сделку на себя независимо от assigned_to в POST, видит/редактирует только свои записи и не может менять ответственного. Чужая карточка/редактирование — 404; удаление менеджеру — 403. Администратор видит все записи, назначает только активного пользователя, переназначает и удаляет. После удаления пользователя сделка остаётся без ответственного и доступна администратору для переназначения; при сохранении формы он обязан выбрать активного сотрудника. Сделки не наследуют ответственного из заявки, поскольку связи с заявкой нет.

Карточка клиента содержит только доступные пользователю сделки, без чужих ссылок и названий. Самих клиентов обе роли видят по прежним правилам. Клиент со сделками защищён от удаления: выводится понятное сообщение и данные сохраняются. Удаление сделки не удаляет клиента. Изменения — только POST с CSRF, GET подтверждения не меняет БД, PUT/DELETE не поддерживаются. Drag-and-drop, графики, email и новые фоновые процессы не добавлены.

Ограничения: прямой ORM save не вызывает full_clean; проверки точности/длины и активного назначения относятся к ModelForm, положительная сумма дополнительно ограничена БД. Списки выбора клиентов/пользователей и сделки в карточке клиента без отдельной пагинации. Production/нагрузка/конкурентность не проверены.

## Воронка продаж — Kanban (6Б.1)

Откройте «Сделки» → «Воронка продаж» (`/deals/kanban/`). Альтернативный список `/deals/` сохранён; ссылка на доску есть и в карточке сделки. Используется та же Deal, без новых таблиц, копий этапа и миграций. Колонки и списки выбора строятся из Deal.Stage.choices в порядке new, contact, proposal, won, lost.

Заголовок каждой колонки содержит полное число доступных сделок. Показываются максимум 20 карточек, отсортированных по created_at DESC, pk DESC. Ограничение выполняется SQL LIMIT, а не загрузкой всех записей в Python. При количестве больше 20 ссылка «Посмотреть все» открывает `/deals/?stage=...`. Нулевой этап показывает сообщение. Карточки показывают ID/название со ссылкой, клиента, индивидуальную сумму в рублях с двумя знаками, ответственного и заполненную плановую дату. В карточке выберите этап и нажмите «Переместить». POST `/deals/<id>/change-stage/` использует CSRF и DealStageForm с существующими TextChoices. Успех перенаправляет на фиксированный `/deals/kanban/` и показывает сообщение. Параметры внешнего редиректа игнорируются. Можно переходить между любыми этапами. При действительном изменении сохраняются только stage/updated_at; created_at, клиент, сумма, ответственный и другие поля не изменяются, даже при их подмене в POST. На 1440/1280 px видны все пять колонок; на 768/375 px прокручивается область доски, а не вся страница. До последнего этапа можно дойти прокруткой. Длинный текст переносится внутри карточек. Drag-and-drop отложен до 6Б.2, чтобы отдельно проверить клиентское взаимодействие с сохранением серверных прав/CSRF; сейчас библиотек перетаскивания, REST API и WebSocket нет.

Ограничения: не более 100 карточек на всей доске, полные записи доступны через список. У больших колонок доска может быть высокой; внутренней вертикальной пагинации нет. Счётчики и карточки читаются отдельными запросами, при параллельных изменениях возможен сдвиг между ними; конкурентность/нагрузка не проверены, история этапов и конфликтное редактирование не реализованы.
