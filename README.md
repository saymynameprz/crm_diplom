# Дипломная CRM

Итерация 1: Django 5.2 LTS, SQLite, вход по логину и паролю, защищённая главная страница с именем и ролью, выход только через POST. Активный суперпользователь — администратор, активный пользователь без этого флага — менеджер. CRM-модули пока не реализованы.

## Локальный запуск

Нужен Python 3.12 (проверено на 3.12.14). Команды выполняются из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
python manage.py migrate --noinput
python manage.py runserver 127.0.0.1:8000
```

Откройте `/login/` на локальном сервере. Главная `/` доступна только после входа. Неверные данные показывают сообщение об ошибке; неактивные пользователи войти не могут. Кнопка «Выйти» отправляет POST с CSRF-токеном. GET `/logout/` возвращает 405 и сохраняет сессию. Внешний адрес в `next` отклоняется стандартным `LoginView`.

В новом терминале снова активируйте окружение и задайте `DJANGO_SECRET_KEY`; для сохранения сессий используйте один и тот же ключ через безопасное локальное окружение. Не добавляйте его в Git.

## Администратор и менеджер

В активированном окружении с заданным ключом выполните:

```bash
python manage.py createsuperuser
```

Введите собственные локальные данные интерактивно. Войдите через `/login/` и откройте «Управление пользователями» или войдите напрямую через `/admin/`.

В Admin откройте «Пользователи» → «Добавить пользователя», задайте логин и пароль менеджера. В карточке пользователя оставьте «Активный» включённым, «Статус персонала» и «Статус суперпользователя» — выключенными; сохраните. При необходимости укажите имя и фамилию. Публичной регистрации нет, готовые учётные записи не поставляются.

Доступ к Admin разрешён только активным `is_superuser=True`, независимо от `is_staff`. Менеджер с ошибочно включённым `is_staff` также не получит доступ. Используются встроенная модель `User` и стандартное управление пользователями Django; собственных таблиц ролей и миграций нет.

Настройки предназначены только для разработки: `DEBUG=True`, разрешены локальные хосты, SQLite, язык интерфейса русский, хранение времени UTC. Для production требуется отдельная конфигурация.

## Проверки

В том же окружении с заданным ключом:

```bash
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
python -m pip check
```

Проверено 26.10.2026: все четыре команды завершились с кодом 0; 20 тестов прошли. Включены неуспешный вход, неактивные пользователи, разграничение ролей (в том числе `is_staff` без `is_superuser`), выход и недоступность главной после него, запрет GET-выхода, безопасный `next`, положительные и отрицательные CSRF-сценарии через `Client(enforce_csrf_checks=True)`.

Реальные HTTP-запросы для обеих ролей проверили вход, неправильный пароль, главную, Admin, `next`, CSRF и выход. В Chromium проверены вход, главная и выход на ширинах 1280 и 375 px; снимки экрана просмотрены, переполнения не обнаружено. Для этих проверок использовалась отдельная временная SQLite, удалённая вместе с проверочными пользователями.

Ручной чек-лист: создайте администратора и менеджера по инструкции; проверьте вход обоих, отображение имени и роли, управление пользователями администратором, запрет Admin менеджеру, сообщение при неправильном пароле и кнопку выхода. Проверьте удобство интерфейса на своём устройстве.

Ограничения: только локальная разработка, production не настроен; нет восстановления пароля, публичной регистрации, ограничения частоты попыток входа и CRM-модулей. Bootstrap в этой итерации заменён небольшим собственным CSS, разрешённым заданием; внешние CDN не используются.
