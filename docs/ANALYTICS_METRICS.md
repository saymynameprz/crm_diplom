# Аналитические показатели CRM — 8А

Это расчёт текущего состояния доступных записей, а не финансовая отчётность или восстановление исторических этапов. `/analytics/` доступна активным авторизованным пользователям. Администратор — активный is_superuser; менеджер — активный обычный пользователь. Каждый queryset ограничивается существующим visible_to **до** COUNT/GROUP BY, отбора периода и чтения денег. Клиенты общие, но это не расширяет доступ к сделкам/истории/задачам. Чужие суммы, количества и ошибки повреждённых сумм не входят в отчёт менеджера. Кэша между пользователями нет.

## Период и момент расчёта

Каждый запрос один раз получает aware `at=timezone.now()`. Он передаётся форме, отбору дат и существующему with_overdue(at). Все даты/подписи UTC.

| Режим GET period | Отбор |
|---|---|
| all (по умолчанию) | Все доступные записи до at включительно |
| 30d | От at−30×24 часа включительно до at включительно |
| custom | start_date 00:00 UTC ≤ поле < (end_date+1 день) 00:00 UTC; дополнительно поле ≤ at |

У сделок поле периода — **Deal.created_at**; у истории — **ClientInteraction.occurred_at**, не created_at записи истории. Заявки и задачи периодом не ограничиваются. Конечный календарный день включается целиком, если уже прошёл; сегодняшнее будущее после at исключается. Custom требует обе корректные даты и конец≥начала; будущие календарные даты отклоняются понятной ошибкой. Формат YYYY-MM-DD. Так не возникает переполнения для даты 9999-12-31 и не учитываются ещё не случившиеся события. Неверный фильтр возвращает 200 с ошибками, показатели периода не показываются как ложные нули; текущая нагрузка остаётся доступна.

Период не возвращает прошлое состояние этапов. Сделка, созданная в период и выигранная позже, учитывается по её **нынешнему** этапу. Даты фактического закрытия/платежей и история просрочек не хранятся. Отдельные SELECT не создают общего транзакционного снимка при параллельных изменениях.

## Метрики сделок

Источник каждой строки — Deal.objects.visible_to(user), ограниченный created_at по указанному периоду. COUNT/GROUP BY stage выполняются SQL, без денежных SUM и загрузки моделей/ForeignKey. Числа целые, не округляются. В нормальных данных каждая сделка входит ровно в один из пяти этапов.

| Название | Формула | Пустые данные | Контрольный пример / интерпретация |
|---|---|---|---|
| Всего сделок | COUNT всех выбранных сделок | 0 | new=1, contact=1, proposal=1, won=3, lost=2 → 8 |
| Новые | COUNT(stage=new) | 0 | 1; текущий этап выбранной когорты |
| Контакт установлен | COUNT(stage=contact) | 0 | 1 |
| Коммерческое предложение | COUNT(stage=proposal) | 0 | 1; это открытая, не успешная сделка |
| Успешно завершена | COUNT(stage=won) | 0 | 3 |
| Проиграна | COUNT(stage=lost) | 0 | 2 |
| Открытые | new + contact + proposal | 0 | 1+1+1 = 3 |
| Закрытые | won + lost | 0 | 3+2 = 5 |
| Конверсия закрытых сделок | Decimal(won) / Decimal(won+lost) × 100 | «Нет данных», если знаменатель 0 | 3/5×100 = 60,0%; 1/16×100 = 6,3% |
| Сумма успешно завершённых сделок | Последовательная сумма Decimal(amount) только stage=won | 0,00 ₽ | 0,01+0,02=0,03 ₽; 9999999999,99+0,01+0,02=10000000000,02 ₽ |

Конверсия округляется **до одного десятичного знака ROUND_HALF_UP**. При won=0/lost>0 это 0,0%, при won>0/lost=0 — 100,0%; это отличается от отсутствия закрытых сделок. Она отражает текущее состояние сделок, **созданных** в период, а не результат сделок, **закрытых** в период, и не историческую динамику конверсии.

Для неизвестного stage показывается отдельное предупреждение и число некорректных доступных записей; шестая колонка не изобретается. Общий итог включает их, open/closed — только известные этапы, конверсия при таком повреждении недоступна. Техническая диагностика записывается в logger crm.analytics без вывода исходного неверного значения пользователю. Для корректных данных total=open+closed; при повреждении total=open+closed+invalid_count.

## Денежные гарантии и пределы SQLite

«Сумма успешно завершённых сделок» **не равна фактически полученной выручке или оплатам**. Платежей в модели нет. Применяются те же права и created_at, что к остальной аналитике сделок. Проигранные/открытые/чужие/не входящие в период сделки не читаются для денег.

Финансового SQL SUM нет. Запрос выбирает только amount для won через values_list и iterator(chunk_size=500), не список всех моделей. Для каждого доступного ORM-значения проверяются Decimal, конечность, диапазон 0.01–9999999999.99 и максимум два знака (по exponent). Ничего не исправляется/не округляется в собственной денежной логике. Сложение выполняется Decimal с localcontext precision=40; это даёт запас для суммы сверх max_digits отдельной сделки. Отображение — два знака и ₽, без преобразования денег во float в бизнес-логике. Пример многих записей: 1001×9999999999,99 = 10009999999989,99 ₽.

Если чтение ORM выбрасывает InvalidOperation/TypeError/ValueError/DatabaseError или значение не проходит проверку, **весь** денежный итог становится недоступным, даже если часть строк уже суммировалась. Страница остаётся 200 и показывает «Финансовый показатель не может быть достоверно вычислен». Частичная сумма/0 вместо ошибки не выдаются. В журнале — техническая причина/traceback; в HTML нет PK, значения чужой сделки или исключения. Счётчики/взаимодействия/нагрузка продолжают рассчитываться независимо.

Доказанные реальные случаи на изолированной SQLite: прямой ORM amount=10000000000.00 сохраняется, затем DecimalField-конвертация даёт InvalidOperation; raw SQL `not-money`/`NaN` даёт ошибку конвертации; 0.001 читается как 0.00 и отклоняется диапазоном. Корректная сумма своего менеджера не ломается из-за повреждённой чужой записи, а администратор видит недоступный денежный показатель.

**Предел гарантии:** SQLite/Django могут округлить до попадания в валидатор: raw SQL 1.234 читается ORM как Decimal('1.23'), а значит аналитика видит/суммирует 1.23. Это подтверждено тестом, не замалчивается как исправление данных. Не все произвольные SQL-повреждения обнаружимы после ORM-конвертации; точность исходного SQLite REAL не гарантируется. Ввод через DealForm и доверенные скрипты Decimal из строк/full_clean остаются обязательными. СУБД/модель денег/миграция в 8А не менялись, production-гарантий нет.

## Взаимодействия

Источник — ClientInteraction.objects.visible_to(user), период по occurred_at. Администратор видит все записи, менеджер свои. SQL COUNT/GROUP BY interaction_type, без округления.

| Название | Формула | Пусто | Контрольный пример / ограничение |
|---|---|---|---|
| Всего взаимодействий | COUNT выбранной истории | 0 | 2 звонка +1 встреча +3 письма +1 комментарий =7 |
| Телефонные звонки | COUNT(type=call) | 0 | 2; ручные записи о совершённых звонках |
| Встречи | COUNT(type=meeting) | 0 | 1; состоявшиеся события |
| Записи о письмах | COUNT(type=email) | 0 | 3; это не число писем, отправленных системой |
| Комментарии | COUNT(type=comment) | 0 | 1; служебные заметки |

Для корректных данных общий итог равен сумме четырёх типов. При прямом повреждении choices неизвестный тип диагностируется отдельно (invalid_count), включён в total, не маскируется под известный тип. История редактируемая, не независимый неизменяемый аудит.

## Текущая нагрузка

Источник — существующие ClientRequest/Task.visible_to(user). Правила просрочки не дублируются: используется прежний with_overdue(at). Менеджеру задача доступна только при совпадении её ответственного и ответственного заявки с этим менеджером; после переназначения рассогласованная задача не раскрывается обоим менеджерам до ручного исправления. Администратор видит всё по прежней политике. Период **не применяется**, числа целые без округления, при пустоте 0.

| Название | Формула | Контроль |
|---|---|---|
| Доступные заявки | COUNT scoped ClientRequest | Своя открытая заявка →1 |
| Доступные задачи | COUNT scoped Task | 3 свои согласованные →3; чужая/рассогласованная не входит |
| Просроченные заявки | COUNT with_overdue(at)=True | Заполненный due_at<at и статус new/in_progress; due_at=at не просрочен |
| Просроченные задачи | COUNT with_overdue(at)=True | Та же существующая семантика; completed/нет срока не просрочены |

Тест: своя заявка с прошедшим сроком и задачи new со сроком −1 микросекунда, new ровно at, completed с прошлым сроком и new без срока → заявки1/просрочены1, задачи4/просрочена1. Этот результат сохраняется при фильтре сделок за 2020 год. Четыре показателя главной не менялись.

## Производительность, проверка и следующий этап

На валидном фильтре — **5 data queries**: 2 COUNT текущей нагрузки, 1 GROUP BY этапов, 1 поток денег, 1 GROUP BY типов истории. Невалидный фильтр —2 (только текущая нагрузка). Auth/session не включены. Нет N+1, чтения полных моделей/FK для аналитики, кэша, новых таблиц/миграций или фоновых задач. Суммирование линейное по числу видимых won; это не нагрузочный аудит.

Контроль HTTP: для когорты менеджера 1 new/1 contact/1 proposal/3 won/2 lost: total8/open3/closed5, 60,0%, сумма10000000000,02; история7. Добавление старой won2,00 даёт all-time total9, сумма10000000002,02; чужие сделки/история не входят. Независимые fixture-контроли и результаты — ITERATION8A_VERIFICATION.md / scripts/verify_iteration8a.py. Все исходные 231 тест сохранены, новые расчёты готовы к использованию как основа 8Б в пределах указанных гарантий. Графики/экспорт/оплаты/новые интеграции не добавлялись; 8Б автоматически не начинается.

## Дополнение 8Б — только представление, 26.10.2026

Предыдущий раздел сохраняет состояние 8А; графики реализованы отдельной 8Б. Все определения/формулы/даты/правила видимости выше остаются без изменений. `crm/analytics.py` побайтно совпадает с 8А. Новый чистый helper `analytics_presentation.py` получает уже рассчитанный отчёт, не обращается к ORM и не меняет исходные целые числа, сумму или конверсию.

| Диаграмма | Числитель | Знаменатель / что означает 100% |
|---|---|---|
| Этапы сделок | counts[stage] из готового отчёта | deals.total: все доступные сделки выбранного периода по created_at |
| Типы взаимодействий | counts[type] из готового отчёта | interactions.total: все доступные события периода по occurred_at |
| Текущая просрочка заявок | workload.requests.overdue | workload.requests.total: текущие доступные заявки независимо от периода |
| Текущая просрочка задач | workload.tasks.overdue | workload.tasks.total: текущие доступные задачи независимо от периода |

Визуальная доля — Decimal(count)×100/Decimal(total), HALF_UP до одного знака. Это оформление количества, не новая метрика конверсии или денег. CSS-ширина — конечная ASCII-строка 0.0–100.0 с точкой, пользовательские строки не подставляются. Неверные типы/отрицательные количества/count>total не превращаются в произвольный style. Нулевой total: доля None/«не определена», ширина0, видимое пустое состояние; у непустого total нулевая категория имеет0,0%. Одна категория с total записями получает100,0%.

Пример: этапы 1/1/1/3/2 при total8 дают12,5/12,5/12,5/37,5/25,0%; типы 2/1/3/1 при total7 дают28,6/14,3/42,9/14,3%. Сумма округлённых долей может быть99,9 или100,1% — дополнительно не нормализуется, точные количества остаются рядом и в таблицах. Просроченная задача1 из3 даёт33,3%, независимо от периода.

Неизвестный stage/type: прежняя диагностика сохранена, полная диаграмма не показывается как достоверная; остаются известные значения таблицы. Ошибка периода скрывает периодные диаграммы без искусственных нулей; текущая нагрузка остаётся рассчитанной. Ошибка денежной суммы не меняет корректные количественные диаграммы, не заменяется0₽, денежная диаграмма не строится.

Графики сопровождаются заголовками/описаниями знаменателей, числами и таблицами; цвет не является единственным носителем значения. No-JS, без анимаций и новых SQL: всего те же5 data queries (2 при невалидном фильтре), оформление0. Остаются все ограничения SQLite/исторической интерпретации/платежей выше. Проверки 267 тестов, HTTP/Chromium и протокол — ITERATION8B_VERIFICATION.md. Финальный этап9 не начат.
