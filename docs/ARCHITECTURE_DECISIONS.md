# Журнал архитектурных решений

## Итерация 2 — 26.10.2026

1. Существующий проект и приложение crm сохранены. Новая Client не связана с пользователем: назначение владельцев не предусмотрено заданием. Обе роли работают с общей базой; удаление разрешено только активному суперпользователю.
2. ModelForm явно перечисляет пять редактируемых полей. Служебные даты задаёт модель, переданные в POST дополнительные поля не сохраняются. Стандартные strip/required и EmailField валидируют форму; длины: имя/организация 200, телефон 50, email 254, примечание 5000. Ограничение примечания сохраняет небольшой объём ручного ввода. Имя, телефон и email не уникальны. Проверки пользовательской формы не означают автоматический full_clean при прямом ORM save.
3. Generic List/Detail/Create/Update/DeleteView и LoginRequiredMixin сокращают собственный код. UserPassesTestMixin перед DeleteView проверяет is_superuser на сервере; менеджеру 403. GET только подтверждает, POST изменяет, HTTP DELETE запрещён. Middleware CSRF оставлен включённым, токены есть во всех изменяющих формах. Стандартные Django messages дают обратную связь.
4. Поиск — ORM Q с OR по четырём полям и icontains. Фильтр организации yes/no применяется вместе с поиском. Две разрешённые сортировки по created_at с pk как вторым ключом обеспечивают устойчивую пагинацию по 10 записей. Неизвестные фильтр/сортировка используют поведение по умолчанию; неверная страница — 404. Django querystring сохраняет параметры в ссылках.
5. SQLite выбран ранее для локальной демонстрации. Его icontains не даёт полноценного Unicode case folding: кириллица ищется с учётом регистра. Подключение расширений БД или Python-фильтрация всей таблицы ради этого в текущую небольшую итерацию не вводились; ограничение явно указано в README. Телефон остаётся строкой без строгого международного формата и нормализации.
6. Существующие шаблоны и собственный CSS расширены; внешние CDN, JavaScript-фреймворки и новые зависимости не нужны. Список карточками переносит длинные контакты на мобильном экране. Текст пользователя экранируется стандартными шаблонами Django.
7. Миграция только добавляет таблицу Client; Django post_migrate также добавляет служебные content types/permissions. Проверка сохранности допускает эти добавления и требует сохранить все исходные строки. HTTP/браузерные сценарии используют временную базу с вымышленными данными.

Источники API: Django 5.2 (BSD-3-Clause), https://docs.djangoproject.com/en/5.2/topics/forms/modelforms/, https://docs.djangoproject.com/en/5.2/topics/class-based-views/generic-editing/, https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes. Использованы стандартные механизмы библиотеки; код сторонних CRM не переносился.

## Итерация 3 — 26.10.2026

1. ClientRequest добавлена в crm без нового приложения. Client с PROTECT сохраняет клиента и связанные заявки при ошибочной попытке удаления. ClientDeleteView перехватывает ProtectedError, показывает ошибку формы без успешного уведомления; проверка на самой операции удаления защищает и от появления связанной заявки после открытия подтверждения.
2. assigned_to использует AUTH_USER_MODEL (фактически встроенный User) и SET_NULL. Удаление учётной записи не удаляет исторические заявки; заявки без ответственного доступны администратору для переназначения. Для обычных операций администратор обязан выбрать активного пользователя, включая активного суперпользователя. При деактивации старого ответственного администратор должен переназначить заявку при следующем сохранении формы.
3. Общий RequestAccessMixin фильтрует queryset менеджера по assigned_to и используется списком, карточкой, редактированием и удалением. Чужая карточка/редактирование дают 404, удаление менеджеру запрещено 403. В карточке общего клиента применён тот же принцип видимости: чужие названия и ссылки не раскрываются. Прежние права менеджеров на клиентов сохранены.
4. ClientRequestForm получает текущего пользователя от view. У менеджера assigned_to исключено из редактируемой формы, подставленный POST не влияет на объект; на создании сервер назначает текущего менеджера. У администратора ModelChoiceField ограничен активными пользователями и обязателен. Клиент проверяется ModelChoiceField, статусы — TextChoices. Название обязательно, 200 символов; описание необязательно, 5000 символов для ограниченного ручного ввода. Все четыре перехода статуса разрешены.
5. Срок необязателен, ввод в datetime-local, UTC и точность до минуты явно показаны. Будущие и прошедшие сроки допустимы, так как автоматического контроля сроков в этой итерации нет. Пустой срок хранится как NULL; даты хранятся timezone-aware. Стандартная Django форма отклоняет неверный формат даты и сохраняет остальные введённые поля.
6. Generic views, SuccessMessageMixin, CSRF middleware и существующие шаблоны расширены без новых зависимостей. Изменения заявок только POST; GET подтверждения безопасен, PUT/DELETE запрещены. Список — таблица с текстовыми и цветовыми статусами; до 600 px строки отображаются блоками с подписями полей. Поиск подстроки, фильтр статуса и две сортировки применяются после ограничения прав; стабильный второй ключ pk и querystring сохраняют пагинацию.
7. Миграция 0002 только добавляет ClientRequest и связи, не изменяет Client/User. Сохранность всех исходных строк проверена на временной базе и базе разработки. HTTP/Chromium используют отдельную временную БД с вымышленными данными. Предыдущие тесты не менялись.
8. По новому заданию задачи и автоматизация разделены в плане на итерации 4 и 5; их реализация не начата. История смены статусов, задачи, уведомления и аналитика не добавлялись.

Ссылки на стандартные API: https://docs.djangoproject.com/en/5.2/ref/models/fields/#django.db.models.ForeignKey.on_delete, https://docs.djangoproject.com/en/5.2/topics/forms/modelforms/. Получение страниц официальной документации из этой среды вернуло proxy 403; поведение PROTECT/SET_NULL дополнительно проверено по исходникам установленной Django 5.2.18 и тестами. Нового стороннего кода и зависимостей нет, лицензия Django BSD-3-Clause указана в README.

## Итерация 4 — 26.10.2026

1. Task добавлена в существующее приложение crm, без автоматического создания. Связь Task.request использует PROTECT: заявки не удаляются вместе с задачами. RequestDeleteView обрабатывает ProtectedError в момент операции и показывает ошибку формы без успешного уведомления. Task.assigned_to использует SET_NULL, сохраняя задачу после удаления пользователя.
2. Task.save() управляет completed_at. Предыдущее сохранённое состояние определяет, нужно ли сохранить старую дату, создать новую или очистить её. Служебная дата editable=False исключена из ModelForm; даже подставленное значение POST не используется. Частичные сохранения поддержаны: при отсутствии status в update_fields используется статус БД, completed_at и updated_at добавляются к сохраняемым полям; пустой update_fields не делает запись. Массовые ORM-операции, обходящие save, не используются для статусов и требуют отдельного решения в будущем.
3. TaskQuerySet.visible_to(user) задаёт единое правило видимости для списка, карточки, редактирования, поиска и связанных задач: у менеджера должны одновременно совпадать assigned_to задачи и заявки. Администратору видны все записи. Queryset применяет правило до поиска/фильтров/пагинации и использует select_related; чужие задачи не раскрывают связанную заявку.
4. TaskForm получает пользователя из HTTP-запроса, а поле request обозначает только связанную ClientRequest. В коде формы используется имя linked_request, чтобы не смешивать сущность с HTTP request. Менеджеру доступны только свои заявки, assigned_to исключено из формы и устанавливается сервером при создании. Администратор выбирает активного пользователя. clean проверяет наличие активного ответственного заявки и совпадение назначений. Правило применяется и при сохранении существующей задачи: рассогласование необходимо исправить администратору.
5. Переназначение ClientRequest пока не меняет старые Task. Старый менеджер теряет доступ через владение заявкой; новый не получает чужую задачу через её assigned_to. Задачи остаются видимыми администратору, который вручную исправляет назначение. В карточке заявки используются те же ограничения. Автоматическая синхронизация и контроль просрочек отложены до итерации 5.
6. Generic views, стандартные CSRF и messages, локальные шаблоны/CSS сохранены. Таблица и статусы используют существующие CSS-классы; новые frontend-зависимости не нужны. Изменения задач только POST, GET подтверждает удаление, менеджер получает 403 на удаление, чужая карточка/редактирование — 404. Поиск/фильтр статуса/сортировки и пагинация 10 повторяют принятый интерфейс; даты UTC, прошедшие сроки разрешены.
7. Миграция 0003 только создаёт Task и связи, не перестраивая Client/ClientRequest/User. Проверка сохранности проведена на базе разработки и временной базе со схемой 0002 и вымышленными данными. Предыдущие тесты/миграции не менялись. Новых библиотек и стороннего CRM-кода нет, применены стандартные API Django (BSD-3-Clause, источники указаны в README).

## Итерация 5 — 26.10.2026

1. Явный сервис create_request_with_task получает новую валидную ClientRequestForm. Он использует её существующие правила прав/назначения и вызывает ensure_automatic_task внутри atomic. View не делает второго save и выдаёт успех только после завершения сервиса; DatabaseError/AutomationError откатывают записи, отображаются как ошибка формы и записываются в журнал. Signals, model.save и фоновые процессы для автоматизации не использованы. Прямые ORM/Admin-операции сами автоматизацию не вызывают.
2. Источник хранится в Task.is_automatic (default=False, editable=False), partial UniqueConstraint ограничивает одну автоматическую задачу на request. Сервис читает текущую заявку, использует select_for_update и get_or_create. Уникальность обеспечивается БД, а не предварительным exists. Повторный вызов возвращает существующую задачу без синхронизации её полей и даты завершения. SQLite select_for_update не блокирует строку; ошибка конкурентной записи может потребовать повтора, отсутствие блокировок не выдаётся за проверенную конкурентную гарантию.
3. Полное название с префиксом/ID и 200-символьным названием заявки не помещается в прежний лимит Task.title. Поле расширено до 255 без обрезания; ручная форма сохраняет лимит 200, автоматическая допускает 255. Это обоснованное изменение предыдущего ограничения, ТЗ не переписано. Признак источника недоступен в форме; связанная заявка автоматической задачи disabled, чтобы редактирование не переносило её к другой заявке и не ломало ключ идемпотентности. Остальные допустимые поля и ручное исправление назначения сохранены.
4. Default due_at автоматической задачи — timezone.now()+24 часа в момент её создания, либо точная копия срока заявки. Заявка без срока остаётся без срока. Старые заявки/задачи не обрабатываются миграцией. Редактирование заявки не создаёт задач и не синхронизирует срок/название/ответственного; это явная граница итерации. Повторный HTTP POST новой формы может создать отдельную заявку; идемпотентность действует на существующий ID заявки. После удаления автоматической задачи её явное повторное создание сервисом допускается.
5. DeadlineQuerySet.with_overdue строит CASE по строгому due_at<at и общим OPEN_STATUSES, без нового поля/статуса БД. DeadlineMixin.is_overdue вычисляет текущее состояние карточки; эквивалентность Python/SQL проверена на всех статусах и границах -1/0/+1 микросекунда и NULL. Одна временная точка применяется ко всем строкам фильтра и отдельно ко всем четырём счётчикам главной. Просрочка не изменяет запись и не зависит от срока/статуса связанной сущности.
6. ClientRequestQuerySet.visible_to вынес прежнюю фильтрацию заявок в общий метод для списков и главной; TaskQuerySet.visible_to сохранил двойную проверку назначения. Поиск, overdue/status фильтры и aggregate выполняются после ограничения доступа. Неназначенные и рассогласованные задачи видит только администратор; новый менеджер не получает их автоматически после переназначения заявки.
7. Task.save не изменён; сервис не меняет статусы через QuerySet.update. Завершение/возобновление управляет completed_at по прежним правилам и влияет только на вычисляемую просрочку задачи, не на статус заявки.
8. Миграция 0004 добавляет False ко всем старым задачам, расширяет поле и создаёт partial unique index без RunPython и backfill задач. Сохранность прежних колонок, количества записей, дат завершения и отсутствие автоматических задач проверены MigrationExecutor, обновлением временной SQLite и базы разработки.
9. Изменения используют Django 5.2.18 (BSD-3-Clause), уже установленный стек и собственные шаблоны/CSS. Сторонние CRM, новые зависимости, email, cron, Celery, Redis, сделки и графики не добавлялись. Ссылки на API: https://docs.djangoproject.com/en/5.2/topics/db/transactions/, https://docs.djangoproject.com/en/5.2/ref/models/constraints/#uniqueconstraint. Подготовлен AUDIT_HANDOFF, независимый аудит ещё не проводился.
