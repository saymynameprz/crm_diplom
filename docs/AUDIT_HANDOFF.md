# Передача CRM для технической проверки

Актуализирован 28.10.2026 по внутреннему аудиту 9А.1 контрольного коммита `dc4564e287e12ad37214750781ee7bd44fdc213b`. Функциональная версия — **8Б + М3Б**, фактически **414 тестов OK**. Это внутренний аудит Codex, не внешняя независимая экспертиза и не окончательная приёмка. Найден P1 в сообщении об ошибке после COMMIT; требуется отдельный 9А.2. Полный протокол — [FINAL_TECH_AUDIT](FINAL_TECH_AUDIT.md), краткий статус — [PROGRESS](PROGRESS.md#audit-9a1). Production не выполнялся.

## Реализованная область

Python 3.12.14, Django 5.2.18, SQLite, серверные шаблоны, локальный CSS и минимальный JS. Стандартный User; активный суперпользователь — администратор, обычный активный пользователь — менеджер. Есть клиенты, заявки, ручные/автоматические задачи, просрочка, сделки, Kanban с проверкой версии, ручная история взаимодействий и аналитика с графиками.

Добавлены чистое математическое ядро М2 (greedy/B&B/oracle, int-минуты/Fraction), административный расчёт М3А и подписанное подтверждение М3Б. Одна новая OptimizationCommit/0007 хранит UUID, автора, digest и созданные ID. Только полный B&B-план, для недоказанного нужно отдельное согласие; клиенты/общий будущий срок UTC проверяются перед атомарным созданием через прежний сервис. Подпись привязана к автору/15 минутам; один токен возвращает прежние ID, новый UUID — новое действие. Экспертные часы/ставки не сохраняются в журнал, глобальных резервов и календарного расписания нет.

Менеджер видит свои заявки/сделки/историю; задача требует совпадения ответственного задачи и заявки. Клиенты общие. Администратор управляет пользователями через Admin; `is_staff` само по себе доступа не даёт. Автор взаимодействия устанавливается сервером и сохраняется при редактировании администратором.

Аналитика использует SQL-ограничения доступа до подсчётов, UTC-периоды all/30d/custom и один момент расчёта. Сделки отбираются по created_at, взаимодействия — по occurred_at. Конверсия `won/(won+lost)` и сумма won вычисляются Decimal; графики получают готовые числа без ORM и финансовых пересчётов. Валидный отчёт — 5 data queries, неверный период — 2, оформление — 0; auth/session в этих измерениях не учитывались. Смысл показателей — [ANALYTICS_METRICS](ANALYTICS_METRICS.md).

## Как повторить проверки

Подготовить окружение и DJANGO_SECRET_KEY по [README](../README.md). Для проверки кода не требуется мигрировать рабочую SQLite:

```bash
python manage.py check
python manage.py test
python manage.py test crm.test_optimization crm.test_optimization_ui crm.test_optimization_commit
python manage.py makemigrations --check --dry-run
python -m pip check
node --check crm/static/crm/kanban.js
```

Django runner создаёт отдельную тестовую БД; миграционные тесты переключают только её схему и возвращают актуальную. Для HTTP/Chromium сохранены [Kanban](../scripts/verify_stage6c.py), [история](../scripts/verify_iteration7.py) и [аналитика](../scripts/verify_iteration8b.py). Им отдельно нужны Playwright/Chromium; артефакты направлять вне репозитория. Команды, охват и ограничения — в протоколах ниже.

**Состояние рабочей БД:** применены CRM 0001–0005; `0006_clientinteraction` и `0007_optimizationcommit` не применены, текущий `migrate --check` возвращает **1**. В 9А.1 рабочая БД не менялась. На синтетической заполненной копии проверены отдельно 0005→0006→0007, сохранены прежние строки/схема, временный migrate --check — **0**. Перед использованием новых функций на своей базе нужны отдельное согласование, backup, применение всей последовательности и перезапуск. Проверка на реальных пользовательских данных не проводилась.

## Открытые вопросы после 9А.1

1. **Деньги и курсор.** SQLite не гарантирует max_digits/scale при прямом ORM/SQL-вводе; raw `1.234` вновь прочитан как `1.23`. Повреждённые суммы в текущем HTTP-отчёте дали 200/недоступный итог. Изолированные 21 OK/exit0 вновь завершились поздним `Cannot operate on a closed database`. Установлена связь с удержанием LogRecord.exc_info/traceback: при обычном небуферизующем handler курсор закрыт, при удержании записи остаётся открыт до её освобождения. Освобождение до закрытия БД устраняет симптом в диагностике. Это не исправление приложения; требуется проверка lifecycle тестовых логов в 9А.2, без автоматической смены финансовых формул.
2. **Конкурентность и подтверждение.** CAS защищает endpoint Kanban; CRUD не имеет общего optimistic locking/единого снимка SELECT. Обычный POST новой заявки не идемпотентен. В М3Б один UUID защищён уникальностью БД и внешней atomic; текущие реальные параллельные HTTP вернули 302/302 и один пакет, отдельная SQLite-блокировка проверена тестами. SQLite select_for_update не даёт строковых блокировок, PostgreSQL/нагрузка не проверялись. Найден P1: после диагностического сбоя ответа уже после COMMIT сообщение ошибочно утверждает «Пакет не подтверждён»; повтор того же UUID безопасен. Детали и минимальный план — в протоколе 9А.1. Журнал/ключ подписи нужно сохранять, новый UUID не обнаруживает логические дубли.
3. **Границы сервисов и форм.** ModelForm и HTTP обеспечивают права/валидацию. Прямые ORM/Admin-записи не вызывают автоматизацию автоматически. Обсудить необходимость общих сервисов редактирования/удаления и модельной валидации назначения; очистка их не добавляла.
4. **Назначения и удаления.** Переназначение заявки не синхронизирует задачи; обеим сторонам менеджеров рассогласованная задача закрыта до ручного исправления. Удалённая автоматическая задача может быть восстановлена сервисом, отдельной истории происхождения нет. Client/автор взаимодействия PROTECT; сотрудника с историей деактивируют, а не удаляют.
5. **Жизненный цикл и время.** Task.save поддерживает completed_at и update_fields; update/bulk обходят save. Завершение заявки/задачи независимо. Просрочка вычисляется на чтении; между запросами время меняется. Проверить UTC, минутную точность UI, все статусы и поведение при конкурентных редактированиях.
6. **Точность описания диплома.** FR-06 частичен: Task связан только с заявкой. FR-08 реализован по уточнённой методике 8А: нет отдельного аналитического счётчика клиентов и полного распределения задач по всем статусам; денежный итог — won. Bootstrap заменён локальным CSS. Аналитика показывает текущие этапы когорты созданных сделок, не историю закрытий/оплаты. Взаимодействия редактируемые; email — запись, не отправка. Требуется явное согласование объёма для защиты, а не автоматическое добавление функций или переписывание ТЗ.
7. **Эксплуатация и доступность.** DEBUG=True и локальные настройки не являются production-конфигурацией. Отдельно оценить HTTPS/cookies/секреты, ограничение попыток входа, резервирование/восстановление, индексы/нагрузку, другую СУБД и доступность. Полный WCAG и все браузеры/физические телефоны не проверены. На узких экранах части исторических DnD-проверок использованы DragEvent/DataTransfer, что не доказывает физическую touch-поддержку; формы доступны без JS. При неопределённом результате сети нужна перезагрузка доски.

Текущие команды/браузерные проверки выполнены заново, а не признаны по старым логам. Нет проверки реальных данных, production, нагрузки, физического touch, других СУБД и восстановления среды в новой задаче. SQLite-поиск кириллицы зависит от регистра, выборы и некоторые связанные списки без пагинации. Экспорта, оплат, рассылок и фоновых процессов нет. Рекомендован отдельный 9А.2 до Д1; внешняя экспертиза, приёмка и дипломные выводы остаются за пользователем. В 9А.1 программный код, тесты и миграции не исправлялись.
