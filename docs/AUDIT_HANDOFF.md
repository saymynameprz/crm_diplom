# Передача CRM на независимый аудит

Состояние: итерации 0–5 реализованы и проверены в текущей облачной среде, 26.10.2026. Независимый аудит ещё не проводился. Следующая функциональность не начата.

## Область реализации

Django 5.2.18, Python 3.12.14, SQLite; стандартный User и роли, клиенты, заявки, ручные/автоматические задачи, текущая просрочка и четыре показателя главной. Собственные серверные шаблоны и локальный CSS. Исходные CRM-репозитории не копировались, зависимости и лицензия Django указаны в README.

## Воспроизводимые проверки

В корне проекта активируйте окружение по README и задайте локальный DJANGO_SECRET_KEY без записи в Git. Выполните:

```bash
python manage.py migrate --noinput
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
python -m pip check
```

Фактический результат текущего запуска: 132 теста, все OK; остальные обязательные проверки — код 0. 110 прежних тестов не менялись. Тесты миграции временно переключают схему crm на тестовой БД и возвращают актуальную; рабочую БД runner не меняет. Перед миграцией своих данных сделайте резервную копию.

## Существенные доказательства

- DB partial unique constraint и повторные сервисные вызовы подтверждают не более одной автоматической задачи на заявку, разрешая ручные задачи.
- Реальный HTTP POST при временном SQLite-триггере отказа откатил заявку и задачу, вернув ошибку формы с сохранённым текстом. После снятия триггера создание прошло. Триггер и временная БД удалены.
- Фиксированное aware-время в тестах, все статусы, срок -1/0/+1 микросекунда и NULL: Python/SQL-просрочка совпадают. Завершение/возобновление не меняет статус заявки и сохраняет правила completed_at.
- Два менеджера и администратор проверены через HTTP: прямые URL, POST-подмена, overdue-фильтры, показатели, переназначение и ручное исправление. Показатели дополнительно сверены с SQL по заданным ограничениям доступа.
- Обновление схемы 0003→0004 сохранило прежние значения и не создало задач для старых заявок. Это проверено unit migration test, отдельной временной SQLite и базой разработки.
- Chromium 154 на 1280/375 px: главная, фильтры/пагинация, создание автоматической задачи, завершение/возобновление; снимки просмотрены, нет JS-ошибок, горизонтального переполнения и HTTP 5xx. Локальные артефакты: /workspace/validation/iteration5/; они не являются файлами репозитория и не обещаны в новой среде.

## Приоритетные вопросы аудитору

1. Проверить границы доверия сервисов и форм: права выдаются HTTP-представлениями/ModelForm; прямые ORM/Admin-операции сами автоматизацию не вызывают. Нужны ли в дальнейшем единые сервисы также для редактирования/удаления и модельная валидация назначения?
2. Проверить идемпотентность и конкурентность на целевой СУБД. SQLite select_for_update не блокирует строку, уникальный индекс не устраняет ошибки lock. Два POST новой формы создают разные заявки. Нужны ли ключ идемпотентности HTTP, политика повторов и проверка одновременных записей?
3. Согласовать удаление автоматической задачи: текущая схема допускает её явное восстановление сервисом после удаления; история происхождения не хранится отдельно. Связь автоматической задачи в UI неизменяема. Нужны ли аудит действий/архивирование?
4. Проверить политику переназначения, удаления и деактивации пользователя: старые задачи не синхронизируются, обеим сторонам менеджеров рассогласованная задача закрыта, администратор исправляет её вручную. Нужны ли отдельные правила синхронизации вместо этого ограничения?
5. Проверить жизненный цикл completed_at при конкурирующих редактированиях и массовых ORM-записях. save(update_fields=...) покрыт; update/bulk обходят save. Завершение заявки и задачи независимо.
6. Проверить SQL/Python-правила текущей просрочки, обновление на GET, часовые пояса и точность минут UI. В списке и счётчиках используется снимок времени, новые загрузки естественно могут дать другие значения.
7. Отдельно оценить production-настройки, HTTPS/cookies/секреты, DEBUG=True, ограничение попыток входа, резервирование и восстановление, индексы/нагрузку и доступность интерфейса. Эти проверки не являются выполненными в текущей итерации.

## Непроведённые проверки и ограничения

Нет нагрузочного/конкурентного тестирования, production-развёртывания, проверки другой СУБД и восстановления облачной среды в новой задаче. Не проверены реальные данные и сторонние браузеры. Поиск кириллицы зависит от SQLite, списки выбора и связанные списки без отдельной пагинации. Email, фоновые задания, сделки, Kanban, история взаимодействий и полноценная аналитика отсутствуют.

Материалы для ручной приёмки и полный журнал результатов: README.md, docs/PROGRESS.md и docs/ARCHITECTURE_DECISIONS.md. Этот документ фиксирует готовность к независимой проверке, а не её успешное прохождение.
