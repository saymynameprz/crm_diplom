## 4. Математика и воспроизводимость

S: в [optimization.py](../crm/optimization.py) каждая работа назначается один раз квалифицированному сотруднику, p≤A−L; L входит в U=(L+p)/A один раз, стоимость только новых работ. C0 — сумма максимальных квалификационных c_ij, включая невмещающиеся альтернативы; нулевая сумма заменяется 1 рублём, пустая квалификационная строка не нормируется выдуманным максимумом. C/U/T/F — Fraction; float только в таймерах. Greedy минимизирует точное ΔF/ID. LB — независимые минимальные оставшиеся стоимости + текущая U; при неотрицательных весах она не превышает любое продолжение. Отсечение только `LB>best`, равенство исследуется ради канонического tie. OPTIMAL/INFEASIBLE требуют доказательства; при лимите — FEASIBLE_NOT_PROVEN/UNKNOWN. Oracle не использует B&B-отсечения; его m^n ограничено.

E: М1 — greedy C=1000, T=13/4, F=23/26; B&B/oracle C=600, T=3, F=19/26, U=1, назначение (второй, первый). Улучшение F=4/23≈17.39%, только на искусственных оценках. Дополнительный одноразовый расчёт **по прямым определениям без helpers ядра** проверил 250 новых малых задач (92 допустимых/158 невыполнимых), совпадение F/C/U/T/C0/канонического вектора B&B и oracle; 193 префикса удовлетворили LB≤минимум продолжений. Это выборка плюс обоснование границы, не доказательство отсутствия всех ошибок.

## 5. Углублённая проверка М3Б

S: [optimization_commit.py](../crm/optimization_commit.py) связывает исходный и prepared-снимки с автором/UUID/issued. Повторная подпись не продлевает исходный TTL. Перед новым сохранением перечитываются выбранные User/клиенты, сравниваются логины/fingerprints, выполняется evaluate_assignment; ClientRequestForm и старый create_request_with_task используются внутри внешней atomic. Уникальный INSERT журнала предшествует бизнес-записям; отдельный exists не является защитой. На SQLite это писательская блокировка, select_for_update не объявляется строковой. Журнал/заявки/задачи откатываются вместе.

E на настоящем временном HTTP:

- М1/предпросмотр не пишут в CRM. После финального подтверждения +2 заявки new, +2 единственные автоматические задачи и +1 журнал, правильные клиенты/исполнители/общий future due_at.

## 7. SQLite, деньги и отложенный курсор

E, прямые значения в синтетической SQLite и GET аналитики:

| Raw amount | Чтение ORM | Итог won / HTTP |
|---|---|---|
| 10000000000.00 | InvalidOperation | None / 200 |
| not-money, NaN | TypeError | None / 200 |
| 0.001 | 0.00 | None / 200 |
| 1.234 | **1.23** | **1.23 / 200** |

Формы/full_clean отвергают переполнение/лишнюю точность. SQLite при прямой записи не обеспечивает scale/max_digits, а после ORM-округления 1.234 первоначальная точность утрачена и уже не диагностируется аналитикой: K, не исправлено. Денежного SQL SUM нет, частичная сумма при обнаруженной ошибке не показывается. Текущий verify_iteration8b подтвердил роли/изолированную повреждённую сумму/ошибочные фильтры.

Изолированные 21 тест воспроизвели исторический `cursor_iter → cursor.close → Cannot operate on a closed database` **после OK/exit0**. Одноразовая диагностика с настоящим курсором и sys.unraisablehook показала:

| Обработка LogRecord с exc_info | Курсор после won_amount | После закрытия БД |
|---|---|---|
| Не удерживать запись | Закрыт сразу | Нет unraisable |
| Удерживать traceback/record | Открыт даже после gc.collect | При освобождении — ProgrammingError |
| Освободить record и собрать GC до close БД | Закрывается | Нет unraisable |

Причина S+E — retained traceback ошибки ORM-конвертера удерживает вложенный cursor_iter; его finally отрабатывает позже соединения. Это соответствует assertLogs lifecycle, а не доказанному HTTP500. Нормальные HTTP-отчёты дали 200/None. Нельзя объявить исправление или автоматически менять деньги/Deal/Django. Минимальный следующий шаг — контролируемое освобождение тестовых записей логов и регрессия; необходимость изменения приложения при буферизующем logging оценивать отдельно (A-02).

## 9. Реестр замечаний и минимальные предложения

### A-01 — P1, неверное сообщение после успешного COMMIT — OPEN

Файл [views.py:697](../crm/views.py#L697), `optimization_confirm`, catch-all на строках 700–702. Условие: commit_snapshot успешно вернул записанный журнал, затем формирование redirect/ответа выбрасывает исключение. В диагностическом временном сервере одноразовый fault в `crm.views.redirect` сработал **после видимого COMMIT**, без изменения исходников.

Факт E: HTTP503 с «**Пакет не подтверждён**», но БД уже получила +2 заявки/+2 задачи/+1 журнал. Повтор того же токена вернул прежние ID без роста. Ожидание: сообщить неопределённость доставки результата/возможное успешное сохранение, сохранить безопасный повтор того же токена. Влияние: ложное описание статуса важной операции может побудить создать новый UUID/ручной дубль или ошибочно считать выполненным rollback. **P0-дубли одного токена/частичный COMMIT не обнаружены.** P1 относится к восстановлению после ошибки и достоверности сообщения, а не к нарушению транзакции.

Минимальное исправление для отдельного 9А.2: нейтральный текст и соответствующий лог «не удалось получить результат; пакет мог быть создан; повторите это же подтверждение», либо явное разделение этапа commit и подготовки ответа. Не менять внешнюю atomic/уникальность. Регрессия: одноразовый сбой redirect после успешного сервиса, проверить сохранённый полный пакет, корректный неопределённый текст и второй POST с теми же ID/без роста. Воспроизведение: синтетическая 0007 → М1 → prepared → fault redirect → final503 → SQL счётчики → повтор того же signed snapshot. При обычном успешном прогоне этот fault не возникал самопроизвольно.

### A-02 — P2 + KNOWN_LIMITATION, lifecycle захваченных traceback — OPEN

[analytics.py:80](../crm/analytics.py#L80), won_amount/logger.exception; [test_analytics.py:140](../crm/test_analytics.py#L140), assertLogs с удерживаемыми records. Предложение: в 9А.2 сначала проверить/исправить lifecycle тестовых логов, освобождать raw LogRecord до teardown после проверки строк; добавить unraisable/retention-регрессию. Не добавлять GC в рабочий HTTP и не менять финансовые формулы автоматически. Поддержка буферизующего logger требует отдельного решения о детерминированном закрытии.

### A-03 — P2, два неточных утверждения тестов М3Б — OPEN
