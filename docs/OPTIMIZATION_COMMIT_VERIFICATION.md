## Подтверждение и доверенные данные

После расчёта `/optimization/` выдаёт кнопку подготовки только для полного B&B OPTIMAL/FEASIBLE_NOT_PROVEN. Greedy-план не сохраняется. Снимок Django signing содержит канонические проверенные экспертные поля, выбранные логины/ID, точный вектор, C/U/T/F/C0, статус/узлы/причину, UUID4, автора и исходное время. Срок — **900 секунд от расчёта**, подпись предпросмотра его не продлевает. Токены передаются только POST, не в URL или общей сессии. Подпись не является шифрованием; видны только данные расчёта текущего администратора, секретного ключа в HTML нет.

Сценарий без JavaScript:

1. POST `/optimization/prepare/`: проверить исходный снимок, показать оценки и назначения; выбрать существующего клиента каждой строки, описание до 1000 символов, начало горизонта и один общий будущий due_at в UTC. Отдельно подтвердить соответствие A/L этому горизонту и экспертный характер оценок. Доступные часы из календарной разницы не вычисляются.
2. POST `/optimization/preview/`: проверить поля и действующую ClientRequestForm, показать полный неизменяемый предпросмотр и подписать его вместе с клиентами/их fingerprints, описаниями и датами. На этом этапе записей ещё нет.
3. POST `/optimization/confirm/`: явная кнопка/checkbox создания, дополнительное согласие для FEASIBLE_NOT_PROVEN; повторная серверная проверка и одна внешняя транзакция. После успеха redirect на `/optimization/result/<uuid>/` с созданными ID и ссылками; результат доступен только своему активному суперпользователю.

Пределы М3А сохраняются: 1–6 заявок, 1–4 сотрудника, 24 пары, 10000 узлов/1 с кооперативного B&B. Математика — целые минуты и Fraction; округление только для отображения. Для новых этапов тело ограничено 256 КиБ, подписанное поле — 128 КиБ, описание — 1000 символов (обычная ручная форма с прежними 5000 не менялась), дата — 32 символа. Неожиданные поля/дубликаты скалярных ключей отклоняются. Во view не вычисляются заново C0 или F.

Перед новым сохранением повторяются HMAC/TTL/авторство, серверная валидация исходной формы, проверка логинов/активности выбранных User, полноты и точных метрик через **evaluate_assignment М2**. B&B повторно не запускается: исходный статус защищён подписью, а новый временной cutoff мог бы изменить уже показанный план. Полнота, квалификация, мощность и метрики проверяются независимо от подписи. Клиенты проверяются по ID и digest всех полей, включая updated_at; удаление/изменение отклоняет старый предпросмотр. Фактическая экспертная занятость независимо не хранится, поэтому её изменение система не обнаруживает и такого обещания нет.

Активный суперпользователь проверяется на каждом маршруте и заново внутри записи. Менеджеры, включая is_staff, не могут подготовить/подтвердить пакет; анонимные направляются на login. Для всех POST нужен CSRF. Новые/ошибочные ответы private/no-store. Подмена исполнителей, статуса, метрик, названий или исходных оценок в скрытых полях не принимается. Ошибки имеют понятные 400/403/409/410; технический сбой/занятая SQLite — 503 с безопасным повтором. Traceback записывается в серверный лог, не в ответ.

## Атомарность и идемпотентность

Разрешённая единственная модель **OptimizationCommit**, миграция **0007_optimizationcommit**: UUID primary key (уникальность БД), created_by PROTECT, digest SHA-256 канонического пакета, created_at, JSON созданных local/request/task/employee ID. Полные экспертные ставки, трудоёмкости, клиенты и описания в журнал не сохраняются. Отдельных таблиц рекомендаций/резервов нет.

Сервис `commit_snapshot`:

- Проверяет подпись/автора и ранее проведённый UUID. Совпавший digest возвращает прежний результат; иной — конфликт.
- Для нового UUID проверяет TTL/математику, затем **первым SQL внутри внешней atomic делает уникальный INSERT журнала**. Это исключает гонку проверки exists→create как основу защиты.
- Внутри той же транзакции повторно проверяет администратора, выбранных сотрудников/клиентов, горизонт/будущий срок. Каждую строку вновь валидирует через ClientRequestForm с текущим администратором и вызывает неизменный create_request_with_task. Проверяет статус new, единственную автоматическую задачу, общего ответственного и одинаковый due_at. Fallback now()+24 часа не используется.
- После всех строк ещё раз проверяет срок/TTL и записывает созданные ID в журнал. Любая ошибка откатывает заявки, задачи и сам журнал вместе. Вложенные atomic прежнего сервиса сохраняются.

На SQLite строковые select_for_update не считаются защитой: уникальный INSERT берёт писательскую блокировку; другой запрос либо читает уже завершённый результат, либо получает уникальный конфликт/контролируемую блокировку. После rollback IntegrityError проверяется существующая запись, OperationalError даёт повтор **того же токена** без скрытого автоматического создания. Поддерживающие backend получают также блокировки выбранных строк; PostgreSQL не проверялся.

Для уже успешного UUID допустимо вернуть прежние ID после TTL/прошедшего срока или изменения исполнителя: HMAC/автор/digest всё ещё проверяются, новых записей нет. Для нового пакета истёкший снимок запрещён. Это осознанное разделение чтения результата и нового подтверждения. Журнал необходимо сохранять; ручное удаление/изменение нарушает долговременную защиту. Новая независимая UUID — новое действие, а не обнаружение всех логически похожих заявок. Ротация ключа подписи инвалидирует старые токены; ключ нужно сохранять между перезапусками.
