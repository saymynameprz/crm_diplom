Исходные **267 CRM-тестов OK**, 6.935 с: запущены все 13 прежних тестовых модулей из этого коммита. Исследование использует только синтетические входы, без ORM/сервера и рабочей SQLite. ## 1. Модель и границы реализации

Контракт — [OPTIMIZATION_MODEL](OPTIMIZATION_MODEL.md), разделы 3–10. Выбрана задача B: назначение пакета новых планируемых работ, а не переназначение существующих объектов CRM. Каждая заявка имеет одного квалифицированного исполнителя; новые трудозатраты не превышают H=A−L. Стоимость c=t·r; цель F=αC/C0+βU, U=max_j((L_j+p_j)/A_j), α+β=1. C0 — сумма максимальных стоимостей допустимых пар по строкам; при нулевой сумме — 1 рубль. Дорогие квалифицированные, но не вмещающие работу альтернативы остаются в нормировке, как в М1.

Математические формулы М1 не менялись. T — суммарные человеко-часы, не календарное время завершения. Расписания, подтверждения индивидуальных дедлайнов, реальной зарплаты и экономии денег предприятия здесь нет. Структура Employee представляет выбранный пул расчёта; будущая проверка активности User относится к М3.

## 2. Архитектура и числовой контракт

Один чистый модуль [crm/optimization.py](../crm/optimization.py) содержит frozen dataclasses Employee/Request/Problem, Metrics/Result, Status и три метода. Он импортирует только стандартную библиотеку. Входы передаются явно, сортируются в локальной копии по стабильным целочисленным ID и не изменяются; допускаются tuple/list последовательности. Отсутствующая пара в Request.efforts означает a_ij=0, неизвестный или повторённый ID пары — INPUT_INVALID.

Рабочее время внутри — **целые минуты**: capacity_minutes, occupied_minutes и положительные минуты каждой допустимой пары. Внешний перевод hours_to_minutes принимает int/Fraction/конечный Decimal часов; умножает на 60 и отклоняет непредставимую долю минуты. Скрытого округления нет. Ставка — руб./час; стоимость пары вычисляется Fraction(minutes,60)·rate. Ставки и веса принимаются как int/Fraction/конечный Decimal, float и bool запрещены. ID/минуты — именно int, bool не подходит. Проверяются уникальность, A>0, 0≤L≤A, r≥0, допустимые веса с точной суммой 1 и корректность структуры.

Все C/U/T/F/C0 — Fraction. Decimal используется только для точного преобразования ввода и округлённого отображения, которое не влияет на выбор. JSON хранит числитель/знаменатель и отдельную display-строку. Float применяется только к секундным таймерам и измерениям времени. Нулевой пакет определён даже без сотрудников; непустой без исполнителей не имеет допустимого решения.

Пример независимого от Django вызова:

```python
from fractions import Fraction
from crm.optimization import Employee, Request, Problem, branch_and_bound

problem = Problem(
    requests=(Request(1, ((1, 60), (2, 60))),
              Request(2, ((1, 120), (2, 135)))),
    employees=(Employee(1, 120, 0, Fraction(100)),
               Employee(2, 135, 0, Fraction(400))),
)
result = branch_and_bound(problem)
assert result.metrics.objective == Fraction(19, 26)
```

## 3. Алгоритмы, доказанность и независимый контроль

**Greedy:** возрастающий local ID; только квалифицированные вмещающиеся пары; минимум точного ΔF, затем меньший user ID. Возврата к прежним решениям нет. Успешный нетривиальный ответ — FEASIBLE_NOT_PROVEN, тупик — HEURISTIC_FAILED без назначения/метрик. При заведомо пустой квалификационной строке возможен предварительный отказ до попыток назначения: нормировка пустого максимума не вычисляется.

**DFS B&B:** стартовый incumbent только из полного greedy; при его неудаче поиск продолжается. Нижняя граница — независимые минимальные стоимости оставшихся индивидуально вмещающихся работ плюс текущий максимум загрузки. Это релаксация конкуренции за ресурс; сумма не завышает возможное продолжение. Пустое множество кандидатов отсекает конкретную ветвь. Стоимостное отсечение только при LB>Fbest, равенство исследуется ради лексикографического минимума. Ветви обходятся по (ΔF,user ID); равные полные оптимумы сравниваются по вектору ID сотрудников в порядке заявок.

Для префикса P используется `LB(P)=α·(C(P)+Σ_remaining min_fitting c_ij)/C0+β·U(P)`. Любое допустимое продолжение выбирает для каждой оставшейся заявки одну из этих пар, поэтому его дополнительная стоимость не меньше суммы независимых минимумов; положительные минуты не уменьшают U. При неотрицательных весах LB≤F любого продолжения. Все допустимые назначения представлены путями дерева, отсечение по мощности исключает только недопустимые продолжения, а строгое стоимостное отсечение не исключает лучший либо равный канонический ответ. Доказательство полного результата требует исчерпания оставшегося дерева; остановка по лимиту его не заменяет.

Каждый полный лист заново проверяется прямым evaluate_assignment по определениям, без доверия инкрементальному состоянию. Структурные доказательства B&B: отсутствие работников/квалификации, индивидуальной мощности либо превышение суммой минимальных часов всей остаточной мощности. Их обратные утверждения не используются. Полный поиск — OPTIMAL или INFEASIBLE. Худший случай остаётся экспоненциальным m^n; сокращение посещённых узлов не является доказательством полиномиальной сложности.

**Oracle:** product всех m^n полных векторов, прямой пересчёт квалификации/мощностей/C/U/T/F и минимум (F,вектор). Не вызывает greedy, границу и даже структурные capacity-проверки B&B. Общие только нормализация входа и прямое определение метрик; дополнительные тесты используют собственный независимый расчёт, чтобы не ограничиваться сравнением двух реализаций с общим helper. Guard max_assignments отклоняет чрезмерное перечисление со статусом UNKNOWN, а не INFEASIBLE. В CLI oracle включается только при n≤5 и своём ограничении количества векторов.

### Лимиты и статусы

B&B считает посещённым вошедшее состояние, включая корень и полный лист. Лимит проверяется **перед следующим входом**. Завершение дерева ровно на последнем разрешённом узле всё равно доказательно. Структурный сертификат/пустая задача могут быть обработаны без посещённых узлов. Greedy считает попытки назначения (либо 0 при квалификационном preflight), oracle — проверенные полные векторы; эти счётчики не смешиваются как одинаковые виды работы.

Таймер monotonic_ns стартует до валидации и greedy внутри B&B. Проверка кооперативная, на границе узла: подготовка и один узел не прерываются посередине. Поэтому это защитный лимит, а не жёсткое прерывание процесса. Значение None отключает time guard; 0 останавливает поиск сразу, но не запрещает математический предварительный сертификат. CLI принимает положительные секундные лимиты.

| Статус | Значение |
|---|---|
| OPTIMAL | Исчерпан поиск с лучшим полным планом либо тривиальный пустой пакет |
| INFEASIBLE | Корректный сертификат B&B или исчерпанный точный поиск без плана |
| FEASIBLE_NOT_PROVEN | Полный greedy или incumbent после остановки B&B |
| UNKNOWN | Лимит без полного плана, либо guard размера oracle |
| HEURISTIC_FAILED | Greedy не построил полный план; не доказательство невыполнимости |
| INPUT_INVALID | Нарушен явный типовой/числовой контракт |
| UNSUPPORTED_DEADLINE | Запрошена индивидуальная календарная гарантия, которой модель не даёт |
| TECHNICAL_ERROR | Зарезервирован для будущего адаптера технических сбоев; ошибки программирования core не маскируются этим статусом |

Неожиданные исключения распространяются и дают неуспех теста/CLI. lower_bound в Result равен None: сертификат всего незавершённого frontier и optimality gap не реализованы. Внутренняя LB отдельного узла не выдаётся за глобальный gap. При неуспехе нет C/U/T/F или частичного «допустимого» назначения. Признаки optimality_proven/infeasibility_proven отделены от факта наличия полного результата.

## 4. Генератор и воспроизводимость

Повторно используемый [CLI](../scripts/run_optimization_experiment.py) содержит генератор исследования; дополнительные Python-файлы для него не создавались. Фиксированы Python 3.12, seeds 20261028–20261047, отдельный random.Random и строка `M2-v1:n:m:K:family:rho:seed`; rho записывается канонической дробью p/q, включая 1/1. Системный hash и глобальное состояние random не используются.

Порядок М1: категория и b для каждой заявки; затем ставка/A/доля L/q по категориям каждого сотрудника; затем навыки по (сотрудник,категория). Упорядоченные множества: b={1,2,3,4} ч, q={1/2,1,3/2}, r={100,200,400} руб./ч, A={8,16,40} ч, L/A={0,1/4,1/2,3/4}; равномерный выбор. Навыки — точный Bernoulli через randrange(denominator)<numerator. Основная серия использует rho=3/4; редкие навыки дополнительно заданы вручную, rho=0 и крайние входы покрыты тестами.

В feasible после исходной генерации выбирается контрольный исполнитель каждой работы, дополняются его навыки, затем A_minutes=max(A_draw,480·ceil(W_minutes/[480(1−ℓ)])), L=ℓA. Контрольное назначение явно валидируется прямым evaluator; оно не считается оптимальным. Stress не исправляет квалификацию/мощность. Конструирование feasible смещает распределение входов — поэтому семейства показаны отдельно, а стрессовые не называются заведомо невыполнимыми.

Канонический снимок содержит единицы, отсортированные ID/пары, минуты, ставки и веса p/q. SHA-256 вычисляется по JSON с фиксированными sort_keys/separators; тесты закрепляют конкретный начальный набор и три fingerprints. Эти значения фиксируют реализацию генератора, а не доказывают экономическую достоверность входов. После первых запусков генератор не менялся; каталог ручных контролей дополнен отдельным общим дефицитом мощности, первые 18 входов/результатов проверены неизменными.

## 5. Контрольные примеры и чувствительность

19 ручных контролей, по пять повторений greedy/B&B/oracle: **17 OPTIMAL, 2 INFEASIBLE**; oracle совпал с каждым доказанным полным решением по F, метрикам и каноническому назначению. Greedy дал 14 полных планов; в 3 из 14 B&B строго улучшил F, ещё в 3 случаях нашёл план после тупика greedy. Повторения одного набора не считаются независимыми случаями.

### Пример М1

Все пары квалификационно допустимы; минуты работ — ((60,60),(120,135)), мощности — (120,135), исходная загрузка 0, ставки (100,400) руб./ч; C0=1300, α=β=1/2.

| Метод | Исполнители заявок 1,2 | C, руб. | U | T, чел.-ч | F | Доказательство |
|---|---|---:|---:|---:|---:|---|
| Greedy | 1,2 | 1000 | 1 | 13/4 | 23/26 | Только допустимость |
| B&B | 2,1 | 600 | 1 | 3 | 19/26 | OPTIMAL, 5 узлов |
| Oracle | 2,1 | 600 | 1 | 3 | 19/26 | Все 4 вектора |

Два остальных вектора нарушают мощность (180>120 или 195>135 минут). Улучшение F=4/23≈17.3913%, стоимости40%, трудозатрат1/13≈7.6923%; U не улучшилось. Это один искусственный пример, не статистика реальной экономии.

### Изменение предпочтений и исходных оценок

Одна работа1ч; A имеет мощность1ч и ставку100, B —4ч и400, L=0, C0=400. Изменяется только α, β=1−α:

| α | Оптимальный исполнитель | C | U | T | F |
|---:|---|---:|---:|---:|---:|
| 0 | 2 | 400 | 1/4 | 1 | 1/4 |
| 1/4 | 2 | 400 | 1/4 | 1 | 7/16 |
| 1/2 | 1 | 100 | 1 | 1 | 5/8 |
| 3/4 | 1 | 100 | 1 | 1 | 7/16 |
| 1 | 1 | 100 | 1 | 1 | 1/4 |

Greedy здесь совпал с точным ответом. Переключение A/B отражает предпочтения, а не измеренную эффективность персонала.

Для четырёх отдельных возмущений примера М1 метрики указаны как C;U;T;F:

| Изменение только одного входа | Greedy | B&B | C0 |
|---|---|---|---:|
| t второй работы у B:135→150мин | HEURISTIC_FAILED | 600; 1; 3; 5/7 | 1400 |
| A первого сотрудника:120→180мин | 300; 1; 3; 8/13 | 600; 2/3; 3; 22/39 | 1300 |
| Ставка B:400→500руб./ч | 1225; 1; 13/4; 57/65 | 700; 1; 3; 93/130 | 1625 |
| L первого сотрудника:0→30мин | HEURISTIC_FAILED | 1000; 1; 13/4; 23/26 | 1300 |

При увеличении мощности A жадный план стоит300, точный600, но F снижается с8/13 до22/39 за счёт U=2/3. Поэтому улучшение многокритериальной F не тождественно денежной экономии. Рост t или L может создать жадный тупик или изменить сам допустимый оптимум.

Нормировка чувствительна к невыбранным альтернативам: в одноработном примере при α=3/4 базовый ответ A с F=7/16. Добавление квалифицированного сотрудника со ставкой10000 и мощностью30мин, которому работа60мин не помещается, увеличивает C0 до10000. Теперь выбирается B: C=400,U=1/4,T=1,F=37/400. F между разными нормировками нельзя сравнивать как выигрыш на одном наборе. Это воспроизводимое ограничение выбранной верхней нормировки М1.

## 8. Выводы и ограничения

1. B&B даёт выигрыш при конкуренции за дешёвых/квалифицированных сотрудников и разной загрузке; конкретный М1 и199улучшений в365сравнимых парах это демонстрируют. Все эти числа относятся только к сформированным искусственным входам.
2. Greedy может занять ресурс, единственный для поздней заявки: ручной trap и14спасённых тупиков основной серии подтверждают ограничение последовательного выбора. Его отказ нельзя представлять доказанной невыполнимостью.
3. На проверенных малых случаях точный поиск доказателен и подтверждён oracle; средние часто ограничиваются бюджетом. Увеличение бюджета до200000 на8крупных случаях улучшило рекомендации, но доказательств оптимальности не добавило.
4. Смена весов меняет рациональный компромисс; меньшая F иногда требует большей C. Экспертные минуты/загрузка меняют допустимость, а C0 зависит даже от неиспользуемой дорогой альтернативы. Требуется проверка предпочтений руководителя, а не обещание универсальной экономии.
5. Для небольшой компании модуль пригоден как исследовательская основа рекомендаций на малых пакетах с явными статусами. Практическая пригодность средних/крупных пакетов, качество экспертных оценок и допустимое время должны подтверждаться отдельно. Нет промышленного испытания, реальных рабочих часов, календаря и экономической валидации.

Остаются: худшая экспоненциальная сложность, фиксированный порядок greedy, слабые LB на симметричных/плотных наборах, отсутствие frontier gap, вырождение U при полностью занятом сотруднике, чувствительность нормировки и смещение feasible-генерации. Нет измерений памяти и доверительных интервалов генеральной совокупности; повторы детерминированного входа не увеличивают число независимых данных.

М3 не реализован: модуль ничего не записывает и не назначает реальным пользователям. Перед интеграцией нужны административные права/CSRF, подтверждённые источники часов/ставок, версии входов, единый учёт мощности, идемпотентность и атомарное создание через прежний сервис. Автоматизация CRM, Task.save, visible_to, Kanban409, история и аналитика не изменялись. Нельзя объявить этот расчёт уже готовым механизмом безопасного сохранения заявок.

### Тесты и независимые сверки

[crm/test_optimization.py](../crm/test_optimization.py) содержит **66 новых тестовых методов** обычного unittest.TestCase. Включены все обязательные исходные, негативные и математические сценарии задания: некорректные типы/точность/веса/ID, пустой пакет, отсутствие квалификации/мощности, М1 с точными дробями, жадный тупик, равные оптимумы, вырождение U, C0, изменение порядка входа, отсутствие мутаций, границы узлов и времени. Дополнительная независимая проверка без изменения файлов сверила 180 малых задач и 167 префиксов с прямыми определениями.
