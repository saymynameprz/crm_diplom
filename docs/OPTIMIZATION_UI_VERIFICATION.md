## Реализация и решения

- `/optimization/`, пункт «Оптимизация заявок». Анонимный направляется на вход; активные менеджеры, в том числе `is_staff=True`, получают 403 для GET/POST. Доступ имеет только активный суперпользователь, независимо от is_staff. Проверка выполняется сервером при каждом запросе; навигация дополнительно скрыта от остальных.
- Размер нового набора выбирается отдельной GET-формой, содержащей только два числа. Экспертные значения отправляются основной POST-формой с CSRF; повторный GET открывает пустой набор. Результаты не помещаются в сессию, общий кэш или БД; ответы имеют private/no-store.
- Список исполнителей серверный: все активные User, как в существующей административной ClientRequestForm, включая суперпользователей. Существование/активность заново проверяются при POST по свежему списку; переданные произвольные ID не принимаются. Отдельной политики «только менеджеры» не введено.
- `OptimizationForm.to_problem()` переводит валидные данные в Employee/Request/Problem. Greedy и branch_and_bound импортируются из неизменного `crm/optimization.py`. Нет копий алгоритмов, пересчёта C0/C/U/T/F во view и SQL из ядра. Отдельный компактный модуль presentation отвечает за округление, русские статусы, таблицы и точное сравнение готовых метрик.
- Источник A/L/r/t — ручные экспертные оценки, не количество задач CRM. H=A−L и исходная загрузка L/A показываются после серверной проверки ввода. Пустая трудоёмкость означает отсутствующую квалификационную пару; положительные оценки обязательны только у допустимых пар. Отсутствующая квалификация всей строки даёт математический результат, а не выдуманную нормировку.
- Отображаются оба метода: полное назначение, C в рублях, U в процентах, T в человеко-часах, F в десятичном виде и точной дробью; узлы/шаги, причина остановки и доказанность. Все восемь кодов М2 имеют разные русские описания. При отсутствии полного плана нет частичных рекомендаций/метрик; недоказанные ответы выделены предупреждением.
- Сравнение использует исходные Fraction: F/C/U/T и разности; относительный выигрыш `(Fg−Fb)/Fg` только при двух полных планах. Обе F=0 дают 0%; нулевая база с ненулевым сравнением — неопределённость. Жадный тупик, спасённый B&B, объясняется отдельно. Снижение C не названо фактической экономией, снижение T — календарной гарантией.

## Жёсткие пределы и числовой ввод

| Параметр | Серверное ограничение |
|---|---|
| Размер | 1–6 заявок, 1–4 сотрудника, максимум 24 ячейки |
| B&B | 10000 посещённых узлов, защитный лимит 1 с; POST не меняет эти константы |
| Время | Целые минуты внутри; A/t от 1 минуты, L от 0; максимум 1000 ч |
| Текст времени | До 8 символов: часы:минуты `2:15` либо десятичные часы `2.25`/`2,25`; до 2 десятичных знаков, без скрытого округления |
| Ставка | 0–1000000 ₽/ч, максимум 2 десятичных знака и 10 символов |
| Веса | 0–1, максимум 2 десятичных знака; α+β точно 1 |
| Заявка | Положительный ID до 999999; название до 120 символов |
| POST | До 16384 байт по CONTENT_LENGTH; чрезмерный запрос — понятный 400 |

Строки проверяются до числового преобразования: нет NaN/Infinity, экспонент, знаков, произвольных дробей и огромных знаменателей. Например, `0.01` ч отклоняется как дробная минута; `0:01` принимается как одна минута. Математика использует Decimal→Fraction и int; float не применяется. Округление ROUND_HALF_UP только в presentation, точные результаты остаются неизменными. Повторы сотрудников, нормализованных локальных ID и скалярных ключей POST отклоняются возле полей. L>A и неверная сумма весов также дают адресные ошибки.

При неверном вводе решатели не вызываются; введённые значения сохранены, ошибки связаны с полями, сводка содержит ссылки на них. Для недопустимого размера либо чрезмерного тела возвращается 400 без построения огромной формы. Успешный расчёт и обычные полевые ошибки — 200; неподдерживаемый HTTP-метод — 405. Технический сбой на границе HTTP логируется с traceback, пользователю возвращаются общий TECHNICAL_ERROR/503 без текста исключения, путей или секретов. Ядро продолжает выбрасывать неожиданные ошибки в прямых тестах.

Таймер М2 кооперативный, включает его подготовку/greedy и проверяется на входе в узел, а не прерывает процесс посередине. Это не жёсткий предел всего HTTP-запроса. При размере 6×4 полное дерево содержит не более 5461 узла; малый размер и ограниченная разрядность — основная защита. Очередь, фоновые процессы и новые зависимости не добавлялись.

## Контрольный пример М1

Два выбранных сотрудника: A=2/2:15 ч, L=0, ставки 100/400 ₽/ч. Две работы с матрицей часов ((1,1),(2,2:15)), α=β=1/2. Это вымышленные оценки.

| Метод | Исполнители работ 1/2 | C | U | T, чел.-ч | F | Статус |
|---|---|---:|---:|---:|---:|---|
| Greedy | Первый / второй | 1000 | 1 | 13/4 | 23/26 | FEASIBLE_NOT_PROVEN |
| B&B | Второй / первый | 600 | 1 | 3 | 19/26 | OPTIMAL, 5 узлов |

Интерфейс показывает улучшение F=4/23≈17,39%. Пример подтверждён тестом с точными ожидаемыми дробями, реальным HTTP и браузером без JS.
