## 1.2 Подходы к автоматизации клиентской работы и распределению заявок

Разрозненный учёт позволяет сохранять отдельные сведения о клиентах, но согласование записей и назначение исполнителей остаются самостоятельной работой сотрудников. Централизованная CRM объединяет связанные операции и задаёт правила их обработки. В исследованиях CRM рассматривается как процесс управления отношениями с клиентами [6]. При этом CRM как стратегия отношений с клиентами и информационная система, поддерживающая эту стратегию, различаются [16, с. 24]. При сравнении решений существенны не только наличие контактов, сделок и задач, но и средства назначения ответственных, наблюдения состояния работы и изменения прикладной логики.

При одинаковом критерии учёта клиентов и сделок в Битрикс24 подтверждены контакты, [сделки и их связи](https://github.com/bitrix24/b24restdocs/blob/30861a483028571723cd0476259eb36435105c20/api-reference/crm/deals/index.md); в amoCRM — контакты, компании, [сделки и воронки](https://github.com/amocrm/amocrm-api-php/blob/a0072fec651b84500c6767f98bbab6d1c8df9ce4/README.md). В разработанной CRM клиент связывает заявки, сделки и взаимодействия. По управлению задачами Битрикс24 документирует [участников, сроки, историю и учёт времени](https://github.com/bitrix24/b24restdocs/blob/30861a483028571723cd0476259eb36435105c20/api-reference/tasks/index.md), amoCRM — [задачи с ответственным, сроком и завершением](https://github.com/amocrm/amocrm-api-php/blob/a0072fec651b84500c6767f98bbab6d1c8df9ce4/src/AmoCRM/Models/TaskModel.php); собственная система — ручные и автоматические задачи заявки без учёта фактически отработанных часов.

По назначению ответственных Битрикс24 и [amoCRM](https://github.com/amocrm/amocrm-api-php/blob/a0072fec651b84500c6767f98bbab6d1c8df9ce4/src/AmoCRM/Models/LeadModel.php) предоставляют программные средства изменения исполнителя [25; 26]. В собственной CRM обычное назначение выполняется через формы, а новый пакет может получить расчётное распределение. Автоматизация различается по подтверждённому объёму: Битрикс24 описывает [вызов внешнего обработчика роботом приложения](https://github.com/bitrix24/b24restdocs/blob/30861a483028571723cd0476259eb36435105c20/api-reference/bizproc/bizproc-robot/index.md), официальная библиотека API amoCRM описывает вебхуки и виджеты для интеграционной логики; это не исчерпывающая проверка встроенных сценариев. В разработанной системе проверены создание автоматической задачи и подтверждаемое создание пакета, без универсального конструктора автоматизации.

По аналитике для Битрикс24 прочитаны [сценарии связи обращения с источником привлечения](https://github.com/bitrix24/b24restdocs/blob/30861a483028571723cd0476259eb36435105c20/tutorials/crm/how-to-use-analitycs/index.md); состав отчётов amoCRM по рассмотренной документации API не установлен. Собственная CRM рассчитывает текущие показатели доступных сделок, взаимодействий и просрочек. По интеграциям коммерческие решения имеют документированный API и механизмы расширения. У разработанного приложения внешняя интеграция не реализована: расчётный модуль подключён внутри системы, что не равно открытому API для сторонних программ.

Реализация конкретного пакетного назначения с ограничениями квалификации, трудоёмкости и мощности в изученных материалах коммерческих продуктов не установлена. Не установлена по ним и возможность воспроизвести именно такой эксперимент с проверкой качества и доказанности распределения. В собственной реализации эти два критерия подтверждаются фиксированной моделью, двумя методами и независимым контролем малых задач. Неподтверждённость в ограниченном наборе источников не означает отсутствия функции во всём продукте; стороннее приложение распределения также нельзя приравнивать к встроенной функции платформы. Различия обосновывают исследовательский выбор, а не функциональное ранжирование CRM.

Ручной выбор исполнителя, назначение по правилам и ротация решают разные организационные задачи. Последовательная эвристика дополнительно оценивает очередное назначение, а комбинаторный поиск рассматривает варианты для всего пакета с учётом ограничений. В данной работе жадный алгоритм и метод ветвей и границ сравниваются для одной модели по расчётной стоимости и максимальной относительной загрузке. Собственная разработка позволяет исследовать эти подходы, показать доказанность результата и связать рекомендацию с явным подтверждением создания заявок. Это контролируемый исследовательский вариант интеграции, а не утверждение о превосходстве учебной CRM или невозможности расширения готового продукта.
